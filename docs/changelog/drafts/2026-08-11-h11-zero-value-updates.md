# Changelog / Devlog — 2026-08-11 H11 Product Update zero-value persistence
**Date:** 2026-08-11
**Source report:** [../../reports/code-review-audit-2026-08-11.md](../../reports/code-review-audit-2026-08-11.md)
**Scope:** backend Go / Gin / GORM
**Trigger:** `ProductRepository.Update` used GORM struct `Updates`, which skips zero-valued fields — admin could never clear `featured:false`, `halal:false`, set `stockQuantity:0` or `basePrice:0`; inventory corrections silently no-op while the UI reports success.
**Result:** **CLOSED end-to-end.** Rounds 1-3 established and regression-tested the three-method repository split (`Update` zero-skip partial / `UpdateAll` full-row zero-write / `UpdateColumns` column-scoped zero-write) in `backend/internal/repository/product/product.go`, but left the zero-capable methods as dead code, so the H11 user-visible symptom still reproduced. Round-4 (owning `internal/handlers/admin/*` + `internal/services/product/product.go`) executed the caller migration: `ProductService` now exposes `UpdateProductAll` / `UpdateProductColumns` (via a separate `productZeroValueRepository` interface type-asserted at construction, so out-of-scope test fakes keep compiling), and all five admin product-write paths route through zero-capable writes — `AdminUpdateProduct` (admin_products.go:252), `AdminUpdateProductStatus` (admin_extensions.go:581), `AdminBatchUpdateInventory` (admin_inventory.go:230), `AdminAITranslateProduct` (admin_ai_translate.go:67) → `UpdateProductAll` (all load-then-patch, so full-row overwrite is safe); the XLSX importer `AdminApplyInventoryImport` → `UpdateProductColumns` with its present-column list. The round-4 arguer correctly REFUTED that importer change: `presentProductColumns` keyed on row-key PRESENCE, and the frontend sends every mapped cell as a string, so a blank cell arrived as `""` and was written as `base_price=0`/`stock_quantity=0`/blanked strings — the same data-wipe failure class as round 1, now per-row on the live `POST /admin/inventory/import-xlsx/apply` endpoint. Round-5 (this round) fixed it: `presentProductColumns` now carries a column only when the cell holds a meaningful value — blank cells and unparseable formatted values (`"$12.50"`, `"1,234.50"`) are skipped (stored value preserved), an explicit zero (`"0"`, `"false"`) is still written (H11 stays closed), and `updated_by` is appended so the importer audit trail is no longer dead. New importer regression tests (blank numeric/string cells, formatted currency, explicit zero, updated_by audit, end-to-end apply) FAIL on the pre-fix path and PASS now. Round-6 (this round) closes the round-5 arguer's refutation: the importer's integer-column gate (`moq`/`stock_quantity`) now matches the actual writer (`toInt`/`strconv.Atoi`) instead of ParseFloat, so decimal/exponent-formatted Excel stock/MOQ cells (`"10.5"`, `"100.0"`, `"1e2"`, `"12.5"`) are skipped exactly like `"$12.50"` and can no longer silently zero stored stock/MOQ while reporting success; `floatCellMeaningful` (ParseFloat, matching `toFloat64`) gates `base_price`; array columns (`images`/`flavors`/`shapes`/`certifications`) get `arrayCellMeaningful` (matching `toStringArray`); and `stringCellMeaningful` now rejects non-string scalars, so a direct-API `{"summary":123}`-style POST can no longer clear stored text. New round-6 tests (unit predicate-vs-writer consistency, present-column edge cases, and two end-to-end apply tests) all FAIL on the pre-round-6 path (proven by temporary revert: decimal stock cell wiped stock to 0; `{"summary":123}` cleared stored text) and PASS now. `go build ./...` PASS; `REDIS_URL= go test ./internal/handlers/admin/... ./internal/repository/product/...` PASS; full `REDIS_URL= go test ./...` PASS (35 packages ok, 0 FAIL) on the clean run — the only failure observed since is `TestCustomerConfirmOrder_NegotiatedInquiryDiscountedTotalSurvives` in `internal/handlers/customer`, an unrelated H10 test another agent is mid-edit on (not touched by H11). Repository layer: complete + tested (rounds 2-3). End-to-end: closed.

## 1. Process
Round 1 confirmed the H11 symptom and shipped `.Select("*")` on the shared `Update`, but the adversarial review proved a live data-destroying regression: the XLSX importer builds a fresh struct from a partial column set and relied on zero-skipping to leave absent columns untouched. Round 2 verified that regression by re-reading `AdminApplyInventoryImport` (`admin_inventory_xlsx.go:515-527`) and split the single method into three explicitly-semantic variants (partial / full-row / column-scoped), restoring `Update` to the importer-safe zero-skip original. Round 2 passed build + full suite, but the round-2 arguer refuted it as a scope claim: a grep for `UpdateAll|UpdateColumns` across `backend/internal/` returns matches only in the test file — no handler, service, or route uses them — so `PUT /admin/products/{id}` with `{"featured":false}` or `{"stockQuantity":0}` still silently no-ops. Round 3 re-read every caller (`admin_products.go:192-262/246`, `admin_extensions.go:550-584/578`, `admin_inventory.go:133-253/224`, `admin_ai_translate.go:41-73/64`, `admin_inventory_xlsx.go:515-527/523`, `services/product/product.go:193-200/224-226`) and confirmed all route through `ProductService.UpdateProduct` → `repo.Update`. Because the importer builds a fresh partial struct (needs zero-skip) while the admin paths build a full loaded row (need zero-write), and both are pinned to the same `Update` method, no single in-file `Update` implementation can serve both; the split is the only correct repository-level resolution, and caller migration is inherently cross-file. Per the owned-file constraint, round-3 edits only `product.go` (in-file WARNING) and the devlog.
## 2. Fixes in detail
#### H11 — ProductRepository.Update cannot write zero values
- **Problem:** `backend/internal/repository/product/product.go` (original `Update`) used GORM struct `Updates`, which skips zero fields, so clearing `featured`/`halal_certified`, zeroing `stock_quantity`/`base_price`, or emptying a text field silently no-oped while the admin UI reported success.
- **Round-1 fix (refuted):** `.Select("*")` on the shared `Update`. It fixed zero-value persistence for the load-then-patch callers but regressed a **live routed endpoint**: `AdminApplyInventoryImport` (`admin_inventory_xlsx.go:515-527`, `POST /admin/inventory/import-xlsx/apply`) builds a **fresh** `modelsProduct.Product` per row, copies only `CreatedAt/CreatedBy/Slug/ViewCount/UpdatedAt/UpdatedBy` from `existing`, and calls `UpdateProduct`. With `Select("*")` every absent column is written as zero — `featured`, dietary flags, nutrition/weight fields, `summary`/`description`/`images`/`flavors`/`shapes`/`ingredients`/`allergens`/`certifications`/`translations`/`gtin` all wiped by a stock-only import. `IncrementViewCount` (`services/product/product.go:193-200`) also newly wrote the zero-column subset on the hot public path.
- **Fix (round 2, `backend/internal/repository/product/product.go`):** split the API into three explicitly-semantic methods, each documented:
  - `Update(ctx, product)` — GORM default zero-skip; restored as the **partial, column-preserving** variant. Byte-identical to the pre-H11 original, so every existing caller (importer, IncrementViewCount, order/COGS paths) behaves exactly as before the finding.
  - `UpdateAll(ctx, product)` — `Select("*")` full-row overwrite **including zero values**; the correct home for H11 semantics. Safe for load-then-patch callers that load the current row first. Doc notes `Select("*")` also places `created_at`/`deleted_at` in the SET column set — harmless for non-deleted rows (writes NULL `deleted_at`; GORM's default scope excludes soft-deleted rows).
  - `UpdateColumns(ctx, product, columns ...string)` — writes only the named DB columns **including zero values**; the column-scoped variant for a partial caller that must clear/zero a specific field (the XLSX importer after migration). Rejects an empty column list.
- **Round-2 adversarial review — ACCEPTED (scope claim):** the repository split is well-formed and regression-free, but the finding's user-visible symptom persists because no production caller migrated. Evidence re-verified this round: a `grep -E "UpdateAll|UpdateColumns"` across `backend/internal/` matches only `product_test.go` and the `product.go` definitions/comments; all 4 admin write paths and the importer still call the zero-skip `Update`. The arguer's reproduction (`PUT /admin/products/{id}` with `{"featured": false}` or `{"stockQuantity": 0}` → silent no-op, success reported) is accurate.
- **Round-3 response (within owned file only):** (1) kept the correct three-method repository API — it is the only correct repository-level resolution, since a struct-based `Update` cannot distinguish "column present with value 0" from "column absent" and both caller families are pinned to it; (2) added an explicit `WARNING` block to `Update`'s doc comment (`product.go:246-254`) naming the unmigrated admin callers and stating that clearing/zeroing from the admin UI still no-ops until they migrate to `UpdateAll`; (3) documented the required migration map below. No behavior change to `Update`.
- **Required coordinated follow-up (out of owned scope — dispatch to handler/service owners):**
  - `AdminUpdateProduct` (`admin_products.go:246`) → `UpdateAll` (loads full row via `GetProductByID`, so full-row overwrite is safe).
  - `AdminUpdateProductStatus` (`admin_extensions.go:578`) → `UpdateAll`.
  - `AdminBatchUpdateInventory` (`admin_inventory.go:224`) → `UpdateAll`.
  - `AdminAITranslate` (`admin_ai_translate.go:64`) → `UpdateAll`.
  - `AdminApplyInventoryImport` (`admin_inventory_xlsx.go:523`) → `UpdateColumns(present-column list)` or merge the full existing row first; keeps partial semantics while allowing a field the row carries as 0 to be zeroed.
  - `ProductService.UpdateProduct` / `IncrementViewCount` (`services/product/product.go:199, 224-226`) → add `UpdateAll`/`UpdateColumns` to the `productRepository` interface and expose pass-throughs; `IncrementViewCount` stays on `Update` (view_count is non-zero).
  - Add one handler-level test asserting `PUT /admin/products/{id}` with `{"featured": false}`/`{"stockQuantity": 0}` persists. That test intentionally does NOT exist yet — it would currently FAIL, which is exactly why H11 is not marked fully closed.
- **Regression tests (existing, passing):** `backend/internal/repository/product/product_test.go` — `TestUpdate_SkipsZeroFields` (pins importer-safe partial semantics), `TestUpdateAll_PersistsZeroValues` (H11 at the repo layer: clears `featured`/`halal_certified`, zeros `stock_quantity`/`base_price`, empties `summary`, unchanged fields survive), `TestUpdateColumns_WritesNamedColumns` (only named columns written incl. zeros; absent columns untouched; empty column list errors). #### H11 — Importer int-cell predicate diverged from its writer (round 6, arguer round-5 refutation)
- **Problem:** the round-5 `numericCellMeaningful` gate for `moq`/`stock_quantity` used `strconv.ParseFloat` (admin_inventory_xlsx.go:668) while the importer's integer writer `toInt` uses `strconv.Atoi` (admin_inventory_xlsx.go:745). A decimal/exponent-formatted Excel integer cell (`"10.5"`, `"100.0"`, `"1e2"`, `"12.5"` — a decimal-formatted stock column or Excel Scientific format is plausible, not exotic) is accepted by the predicate (`ParseFloat` ok → column carried) but `toInt` returns 0 (`Atoi` fails), so on the live `POST /admin/inventory/import-xlsx/apply` the row `{"stockQuantity":"10.5"}` wrote `stock_quantity=0` over the stored value; the update path validates only `product.Name`, so 0 persisted and the endpoint reported `updated:1`. Pre-H11 GORM zero-skip preserved those stored values — the same "formatted value must not wipe data" contract round 5 claimed to enforce, narrowed to the integer columns. The round-5 tests only covered `"$12.50"`/`"1,234.50"` (rejected by BOTH ParseFloat and Atoi, so vacuous) and explicit `"0"`/`"false"`; none exercised the ParseFloat-accept / Atoi-reject divergence. Secondary edge: `stringCellMeaningful` treated any non-string/non-nil value as meaningful, but the scalar string writers type-assert `string`, so a direct-API `{"summary":123}` carried the column and wrote `""`, clearing stored text.
- **Fix (this round, `backend/internal/handlers/admin/admin_inventory_xlsx.go`):**
  - `presentProductColumns` (admin_inventory_xlsx.go:621-655) now dispatches each column to a gate that uses the SAME parser as the writer that produces its value: `base_price` → `floatCellMeaningful` (ParseFloat, matches `toFloat64`); `moq`/`stock_quantity` → `intCellMeaningful` (Atoi, matches `toInt`); `halal_certified`/`oem_available` → `boolCellMeaningful` (matches `toBool`); array columns (`images`/`flavors`/`shapes`/`certifications`, in the new `stringArrayColumns` set) → `arrayCellMeaningful` (matches `toStringArray`: a comma string with a real item, or a `[]interface{}` holding a string item, is carried; blank/empty-part strings and non-string arrays are skipped); scalar string columns → `stringCellMeaningful`. `status` keeps the existing `IsValidProductStatus` special-case.
  - `intCellMeaningful` (new) mirrors `toInt`: string → `strconv.Atoi` on the trimmed value (so `"10.5"`/`"100.0"`/`"1e2"`/`"12.5"` are skipped like `"$12.50"` while explicit `"0"`/`"10"` still carry); `json.Number` → `val.Int64()` (matching `toInt`'s `json.Number` branch); float64/float32/int/int64 → true (matching `toInt`'s truncation path).
  - `floatCellMeaningful` (renamed from `numericCellMeaningful`) keeps ParseFloat semantics for `base_price`, whose writer `toFloat64` also uses ParseFloat — decimal/exponent price strings (`"100.0"`, `"1e2"`) ARE carried because a real value is applied, not a wipe.
  - `stringCellMeaningful` now returns true ONLY for a non-blank string; non-string/nil values are skipped so a non-frontend caller typing a number into a text column cannot blank stored text.
  - The four load-then-patch handler migrations from round 4 and the round-5 blank/formatted-currency behavior are unchanged.
- **Regression tests added** (`backend/internal/handlers/admin/admin_inventory_xlsx_test.go`): unit — `TestIntCellMeaningful_MatchesToInt` (rejects `"10.5"`/`"100.0"`/`"1e2"`/`"12.5"`/`"$12.50"`/`"1,234.50"`/`""` exactly when `toInt` yields 0; carries `"0"`/`"10"`; numeric non-strings meaningful), `TestStringCellMeaningful_RejectsNonString`, `TestArrayCellMeaningful`, `TestPresentProductColumns_ArrayColumns`; present-column edge cases — `TestPresentProductColumns_SkipsDecimalIntegerCells`, `TestPresentProductColumns_SkipsExponentIntegerCells`, `TestPresentProductColumns_CarriesDecimalFormattedFloat` (base_price `"100.0"` carried), `TestPresentProductColumns_SkipsNonStringScalarCell` (`summary:123`, `leadTime:12.5` do not leak); end-to-end — `TestAdminApplyInventoryImport_DecimalStockCellPreservesStoredValue` (`"10.5"` stock cell preserves stored 5), `TestAdminApplyInventoryImport_NonStringScalarPreservesStoredText` (`{"summary":123}` preserves stored text). All primary and secondary pre-round-6 tests were PROVEN to FAIL by temporarily reverting `intCellMeaningful` to ParseFloat (decimal stock cell wiped stock to 0; columns leaked) and `stringCellMeaningful` to the any-non-string version (summary cleared to `""`), then PASS after restore. ## 4. Adversarial review (arguer)

**Verdict: REFUTED** (as a cleanly-shippable fix; the core symptom is fixed but the change regresses a live admin data path).

### What the fix gets right
The H11 symptom is real and the mechanism is confirmed: GORM struct-based `Updates(product)` skips zero fields, so `featured:false`, `halal_certified:false`, `stock_quantity:0`, `base_price:0` silently no-op'd. `Select("*")` does force zero-value writes, and the load-then-patch callers (`AdminUpdateProduct` admin_products.go:192-262, `AdminUpdateProductStatus` admin_extensions.go:550-578, `AdminBatchUpdateInventory` admin_inventory.go:133-246, `AdminAITranslate` admin_ai_translate.go:41-67, `IncrementViewCount` services/product/product.go:193-200) re-assert the full DB row, so for them `Select("*")` is correct. `go build ./...` passes; `REDIS_URL= go test ./internal/repository/product/... ./internal/services/product/...` passes; the new `TestUpdate_PersistsZeroValues` was re-run fresh (`-count=1`) and passes, proving zero-value persistence.

### Concrete regression 1 — XLSX importer now wipes columns absent from the uploaded row (data-destroying)
