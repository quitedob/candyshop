# Changelog / Devlog — 2026-08-11 M2 — useToast hide timers; CSP unsafe-inline; INTERNAL_API_BASE SSR config
**Date:** 2026-08-11
**Source report:** [../../reports/code-review-audit-2026-08-11.md](../../reports/code-review-audit-2026-08-11.md)
**Scope:** frontend Nuxt 3 / Vue 3 / TypeScript / Tailwind
**Trigger:** M2 — (a) `useToast` overlapping hide timers let an older timer dismiss a newer toast; (b) `nuxt.config.ts` CSP used `script-src 'unsafe-inline'` (disables XSS mitigation) and `connect-src https:` (broad exfiltration); (c) `INTERNAL_API_BASE` defaulted to `http://localhost:8080`, so a production deploy setting only `BACKEND_URL` silently pointed SSR fetches at a build machine.
**Result:** All three M2 issues fixed, plus the two residuals the adversarial re-review raised. (a) `useToast` now owns a single per-toast hide timer (cleared on show/hide). (b) CSP hardened: `'unsafe-inline'` removed from `script-src` (the sole inline script, the dark-mode theme init, is pinned by `'sha256-...'`), and `connect-src` narrowed from `'self' https:` to `'self'` plus the configured absolute `API_BASE_URL` origin — so absolute-HTTPS API mode and the order-chat WebSocket keep working (the arguer's regression) while exfiltration to arbitrary HTTPS hosts is closed (the finding). (c) `internalApiBase` resolves `INTERNAL_API_BASE → BACKEND_URL → dev localhost`; the same derived base is mirrored into `process.env.INTERNAL_API_BASE` at config-load time so the build-time `server/plugins/prerender-routes.ts` CMS enumeration (arguer's residual entry point) no longer silently hits a build machine's localhost when only `BACKEND_URL` is set. The missing-both-env production warning is gated to `nuxt build`/`nuxt generate` and suppressed for `nuxt prepare`/`nuxt typecheck` (which force `NODE_ENV=production`), so local typecheck/postinstall are no longer spammed. `npm --prefix frontend run typecheck`: exit 0, 0 `error TS`. All 9 config-load scenarios verified via a jiti harness.

## 2. Fixes in detail
#### M2a — useToast overlapping hide timers
- **Problem:** `frontend/composables/useToast.js:23-27` — every `show()` scheduled a fresh `setTimeout(hide)` without clearing the previous one, so an older toast's timer could fire after a newer, longer-lived toast (or a `duration: 0` persist) was already visible and hide the wrong toast.
- **Fix:** Module-level `let hideTimer = null` (`useToast.js:16`). `show()` clears any pending timer before mutating state (lines 24-27), then stores the new timer in `hideTimer` (36-40). `hide()` clears it too (45-48). Each toast now owns its hide timer; an older timer can never dismiss a newer toast. **Adversary CONFIRMED fixed** — no counterexample found.
#### M2b — CSP: drop `'unsafe-inline'`, scope `connect-src` to the app's own API origin
- **Problem:** `frontend/nuxt.config.ts:37` (pre-fix) — `script-src 'self' 'unsafe-inline'` lets injected inline scripts execute (XSS mitigation off), and `connect-src 'self' https:` permits exfiltration to any HTTPS host.
- **Fix (script-src):** Hoisted the theme-init block into a `themeInitScript` constant and derived `themeInitHash = 'sha256-' + sha256(themeInitScript)` at config load from the *same* constant that populates `app.head.script[0].innerHTML` — the policy can never drift from the emitted script (unhead renders `script.innerHTML` verbatim; independently re-computed `sha256-0wZl+DdUXJd3lIP1DmS1dXhAoGz63DhkXpa9fomNP6w=`). `script-src` is now `'self' 'sha256-…'`.
- **Fix (connect-src, refutation residual):** Instead of a blanket `'self'` (which the arguer showed regresses the documented absolute `API_BASE_URL` mode), `connectSrc` is now derived from the configured API base: `'self'` plus the absolute origin of `API_BASE_URL` when present (`nuxt.config.ts:50-57`). A plain-http origin is only added outside production (that is the documented dev value in `.env.example`); production requires HTTPS. This preserves every client `fetch` and the order-chat WebSocket: `useOrderMessageStream.ts` rewrites `https://<api-host>/…` to `wss://<api-host>/…` on the same host, and CSP matches `ws`/`wss` against an `http`/`https` host-source on the same origin — so `connect-src 'self' https://api.example.com` covers both the fetch and the WebSocket. It still closes the finding's exfiltration surface: only the single configured API origin is allowed, not `https:` (any host). `style-src 'unsafe-inline'` retained (Tailwind/Vue style injection); PayPal/Stripe are navigation redirects (not `connect-src`); Google Maps is an iframe under unchanged `frame-src`.
- **Note:** Nuxt 3 core has no CSP nonce support (requires the community `nuxt-security` module, not installed / out of scope); the `'sha256-…'` hash pins the only inline script without it.
#### M2c — INTERNAL_API_BASE resolution + build-time prerender entry point
- **Problem:** `frontend/nuxt.config.ts:288` (pre-fix) — `internalApiBase` defaulted to `http://localhost:8080/api/v1`; a production deploy setting only `BACKEND_URL` got SSR fetches routed to the build machine's localhost. The arguer additionally identified a second entry point: `frontend/server/plugins/prerender-routes.ts:50` reads `process.env.INTERNAL_API_BASE || 'http://localhost:8080/api/v1'` and never derives from `BACKEND_URL`, so the build-time `prerender:routes` CMS enumeration silently hit localhost during `nuxt build`.
- **Fix:** `internalApiBase` resolves `INTERNAL_API_BASE → BACKEND_URL (trailing-slash-stripped, + '/api/v1') → dev localhost` (`nuxt.config.ts:39`). The same derived value is mirrored into `process.env.INTERNAL_API_BASE` at config-load time when `BACKEND_URL` is set and no explicit `INTERNAL_API_BASE` exists (`nuxt.config.ts:36-38`) — this runs before nitro build, so `server/plugins/prerender-routes.ts` (which runs in-process during `nuxt build` prerender) reads the BACKEND_URL-derived base instead of its own hardcoded localhost fallback. It is inert at runtime (the deployed server never re-executes `nuxt.config.ts`) and never overrides an explicit env var.
- **Fix (warning noise, edge case 3):** The missing-both-env `console.error` is now gated on `isProduction && process.argv[2] ∉ {prepare, typecheck}` (`nuxt.config.ts:59-67`). `nuxt prepare`/`nuxt typecheck` force `NODE_ENV=production` but are not deployments, so the warning no longer spams every local run; it still fires on `nuxt build`/`nuxt generate`, and at runtime the localhost fallback fails fast (SSR connection refused), never silently.
- **Doc drift fixed:** stale comments at `nuxt.config.ts:22-28` and `316-318` that claimed a "hard production failure" now describe the warning + fast-fail fallback accurately.

## 4. Adversarial review (arguer)

**Verdict: CONFIRMED_FIXED.** The prior arguer's two residuals are both closed: connect-src no longer regresses the absolute-`API_BASE_URL` mode, and the build-time `prerender-routes.ts` entry point no longer hardcodes localhost when `BACKEND_URL` is set. I could not construct a scenario where M2 (a), (b), or (c) still manifests, or where the fix regresses a non-affected path. `npm --prefix frontend run typecheck` re-ran to completion: exit 0 (`nuxt prepare` + `vue-tsc --noEmit` both silent-pass).

### (a) useToast — CONFIRMED fixed
`frontend/composables/useToast.js:16` — single module-level `hideTimer`. `show()` clears any pending timer before mutating state and only assigns a new one when `options.duration !== 0`; `hide()` clears too. A `duration: 0` persist toast sets no timer. No sequence hides a newer/longer-lived toast with an older timer. Sole minor note: if `tts.playForToast()` throws, the toast is left visible with no timer (pre-existing, unrelated to M2, and arguably acceptable).

### (b) CSP — CONFIRMED fixed; one documentation error found (wrong hash constant)
- **connect-src regression closed (prior residual).** `nuxt.config.ts:50-57` derives `connectSrc` = `'self'` + the absolute origin of `API_BASE_URL` (`https:` always; plain-http only when `!isProduction`). I audited every client network consumer in the repo:
  - All AI/chatbot/SSE fetches build URLs from `${apiBase}` (`pages/admin/ai/index.vue:245-311`, `pages/admin/trades/[id].vue:424`), i.e. relative `/api/v1` (same-origin → `'self'`) or the single configured absolute origin (added explicitly).
  - Order-chat WebSocket (`composables/useOrderMessageStream.ts:34-43`) rewrites `http(s)://<api-host>` → `ws(s)://<api-host>`; CSP matches `ws` against an `http` host-source and `wss` against an `https` host-source on the same host, so `connect-src 'self' https://api.example.com` covers both the fetch and the `wss://` socket. In the relative mode the socket is same-origin and covered by `'self'`.
  - Stripe/PayPal are `window.location.href` navigation redirects (`pages/customer/orders/[id].vue:887-909`), not `connect-src`; social/WhatsApp/certification share use `window.open` (navigation); contact map is an `<iframe src="https://www.google.com/maps/embed/...">` (`pages/contact.vue:104-113`) exactly matching `frame-src https://www.google.com`; fonts allowed via `style-src`/`font-src`; no `<video>`/`<audio>`; no other WebSocket/EventSource/hardcoded absolute `fetch` exists. The finding's broad `connect-src https:` exfiltration surface is closed.
- **`script-src` is internally consistent but the documented hash is WRONG.** The fixer's verification prose and the prior arguer's "independent re-computation" both cite `sha256-0wZl+...`. That value is the hash of the *source text* with the backslash preserved. JS template literals drop the backslash of an unknown escape, so the **evaluated** `themeInitScript` is `(?:^|;s*)` (255 chars) and its actual sha256 is `sha256-W51RirYHCeaB4X6FnCy1hS4SDKeTRQIWk/JZedYzKdw=`. Because `nuxt.config.ts:20` computes the CSP hash from the same evaluated constant that populates `app.head.script[0].innerHTML` (line 171), the served header and served inline script still match by construction — no functional defect. The `0wZl+...` value in this devlog is factually wrong and should be corrected to `W51R...`; it hashes the raw literal, not the string Nuxt actually emits.
- **Side-effect of the backslash drop (pre-existing, orthogonal):** the theme-cookie regex is effectively `(?:^|;s*)theme=` — a semicolon followed by zero-or-more literal `s` characters. When other cookies precede `theme` (`foo=1; theme=dark`), the required space after `;` is not matched, so first-paint dark-mode detection silently falls back to `prefers-color-scheme`. This predates the hoist and is not an M2 defect, but it is a real (minor) functional bug worth a separate ticket.
- **New edge behavior (note, not refuting):** `new URL(apiBaseUrl).origin` at line 53 now throws at config load for a malformed absolute value like `API_BASE_URL=https://` (the regex matches, then `new URL` rejects), aborting the build — the old pass-through code merely produced a broken base. Garbage input only; a protocol-relative `//host` value is also not matched by the regex, leaving `'self'` while client fetches to `//host` would be CSP-blocked (undocumented mode).

### (c) INTERNAL_API_BASE — CONFIRMED fixed at both entry points
- **Runtime.** `config.internalApiBase` (`nuxt.config.ts:39`) resolves `INTERNAL_API_BASE → BACKEND_URL(+'/api/v1', trailing-slash-stripped) → dev localhost` and is consumed by `composables/useApi.ts:303`, `composables/useAuth.ts:46`, and `server/routes/__sitemap__/cms-urls.ts:4` (all baked at build). The literal finding scenario (prod build sets `BACKEND_URL`, not `INTERNAL_API_BASE`) no longer routes SSR fetches at the build machine.
- **Build-time prerender entry point (prior residual).** `nuxt.config.ts:36-38` mirrors the derived value into `process.env.INTERNAL_API_BASE` at config-load time, before nitro build; `server/plugins/prerender-routes.ts:50` reads that same env var. `nuxt build`/`nuxt generate` evaluate the config in-process and nitro prerender either shares the process or forks a child that inherits `process.env`, so the CMS-route enumeration uses the BACKEND_URL-derived base. Explicit `INTERNAL_API_BASE` always wins; the mutation is inert at runtime (the deployed server never re-executes the config).
- **`isProduction` gating is reliable across every invocation — no silent regression.** Verified in `@nuxt/cli/dist`: `build-CrY4JY0C.mjs:37` calls `overrideEnv("production")` at the top of `run()` **before** `loadNuxt`; `generate-DreRkh3n.mjs` reuses `build_default.run`; `prepare-CNPL0HH9.mjs:27` and `typecheck-C8wVgBzd.mjs:25` set `NODE_ENV ||= "production"`; `dev-ChFC_-E8.mjs:642` calls `overrideEnv("development")`. So `cacheRouteRules` (SWR), `devtools:false`, the connect-src http-block, and the missing-env warning all evaluate correctly for every command — including the fixer's own warning gate (`argv[2] ∉ {prepare, typecheck}`), which is deterministic for the standard npm/nuxi invocations (`package.json` `postinstall`/`typecheck` both run `nuxt prepare`, i.e. `argv[2]='prepare'`, suppressed).
