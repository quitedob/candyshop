# Changelog / Devlog — 2026-08-11 H2 Return Creation IDOR / Refund Fraud

**Date:** 2026-08-11
**Source report:** [../../reports/code-review-audit-2026-08-11.md](../../reports/code-review-audit-2026-08-11.md)
**Scope:** backend Go / Gin / GORM
**Trigger:** `CustomerCreateReturn` blind-inserted a `ReturnRequest` keyed on client-supplied `orderID` + raw-context `userID` with no ownership, status, quantity, or refund validation.
**Result:** Create path loads the order, enforces ownership (403), lifecycle status, per-line quantity (<= ordered minus already returned, and <= shipped/fulfilled when recorded) and refund ceilings; fixed contradictory `required,min=0` binding; serializes the tally+insert with a per-process mutex (closes the single-instance TOCTOU); aggregates the already-returned tally across all pages (no >1000 undercount, fail-closed); echoes persisted items in the 201 body. 12 regression tests; build + package tests green. Residual: the concurrent over-return vector remains open only for multi-instance deployments, where a DB-level guard (repository/model change, out of handler scope) is required — documented.
---

## 1. Process
First pass: read `customer_return.go`, the read-path idiom (`CustomerGetReturn` ownership check), the `ReturnRequest`/`ReturnItem` models, `OrderService.GetOrder`, and the `ReturnRepository`; added ownership/status/quantity/refund validation in the handler (the only owned file) and 8 regression tests reusing the package's `fakeOrderRepo` + sqlite harness. Adversarial review refuted: the ceilings were an unlocked read-then-write (concurrent creates could both pass and persist) and the tally capped at `limit=1000` undercounted. Second pass (this revision): confirmed the handler holds no `*gorm.DB` and `ReturnRepository.Create` opens its own internal transaction on its own handle (`repository/order/return.go:23-46`), so a true DB-level transaction spanning the read and the write is not reachable from the handler-only owned scope; therefore closed the TOCTOU for the single-instance target with a per-process `sync.Mutex`, made the tally page-across-all (fail-closed), capped claimable qty by shipped/fulfilled, echoed persisted items, and documented the DB-constraint remediation for multi-instance. Added 4 tests (3 new + 1 extended).

## 2. Fixes in detail
#### H2 — Return creation is unvalidated (IDOR + refund fraud)
- **Problem:** `backend/internal/handlers/customer/customer_return.go` inserted `ReturnRequest{OrderID: orderID, UserID: userID.(string)}` directly with no ownership, status, quantity, or refund validation. Read path (`CustomerGetReturn`) enforced ownership; create path did not. `OrderItemIdx` also used `binding:"required,min=0"` — `required` rejects `0`, so returns on line index 0 always failed binding.
- **Fix (pass 1):** switch to `contextUserID(c)`; load the order via `h.services.Order.GetOrder` (404 `order_not_found` on lookup error); 403 `forbidden` on `order.UserID != userID`; reject statuses that cannot be returned (`orderStatusAllowsReturn` mirrors `ValidOrderStatusTransitions` source statuses: partially_shipped/shipped/partially_delivered/delivered/partially_returned); per line require a real `OrderItemIdx` with matching `ProductID`, `Quantity` in `[1, line qty − already returned]`, `RefundAmount` in `[0, UnitPrice*Quantity]`, and `Σ refunds ≤ order.TotalAmount`; `binding:"min=0"` for `orderItemIdx`.
- **Fix (pass 2 — refutation response):**
  1. **TOCTOU (concurrent double-claim):** `returnCreateMu` (package-level `sync.Mutex`) is held across the already-returned tally, the checks, and `ReturnRepository.Create` (`customer_return.go:130-131`), so a second concurrent request for the same order+line re-reads the tally after the first commits and is rejected. This closes the race for the single-instance deployment; a multi-instance deployment still needs a DB-level guard (partial unique index on `return_items(order_id, order_item_idx)` where status <> 'rejected', or `SELECT ... FOR UPDATE`/version-guarded insert in the repository), which is out of this handler-only scope and documented at `customer_return.go:34-42`.
  2. **Tally undercount:** `sumReturnedQuantities` (`customer_return.go:50-70`) now pages through ALL of the caller's returns (500/page) instead of the first 1000, fail-closing on error so a claim is never created when the tally cannot be verified.
  3. **Shipped/fulfilled cap:** claimable quantity is capped to `min(ordered, max(shipped, fulfilled))` when the line records such counts (`customer_return.go:156-167`), so a never-shipped line cannot be returned for a refund where shipment data exists.
  4. **Response fidelity:** `ret.Items = items` before the 201 (`customer_return.go:212`) so the create response echoes the persisted lines (repo `Create` populated `ReturnID` + timestamps).
  - Tests: 3 new (`TestCustomerCreateReturn_ConcurrentFullClaim`, `_ShippedQuantityCapsClaim`, `_TallyAcrossAllPages`) + `_Success` extended to assert items in the body (12 total).

## 4. Adversarial review (arguer)

**Verdict: REFUTED** — the primary single-request vectors are closed, but the refund-fraud / over-return class the finding describes is not fully eliminated: the new quantity/refund ceilings are enforced as an unlocked read-then-write and can be bypassed by concurrent requests, and the "already returned" tally silently undercounts past the first 1000 returns.

### What I verified is genuinely fixed
- IDOR is closed: `customer_return.go:74-77` returns 403 when `order.UserID != userID`, using `contextUserID(c)` which reads the same `c.Get("userID")` source as the read path (`customer_extensions.go:22-29`). Verified by `TestCustomerCreateReturn_OwnershipForbidden` (403 + zero rows persisted).
- 404 on lookup: real `OrderRepository.FindByID` returns `(nil, err)` on missing order (`repository/order/order.go:58-64`), so no nil-order panic.
- Status gate mirrors the state machine: `orderStatusAllowsReturn` covers exactly `partially_shipped/shipped/partially_delivered/delivered/partially_returned`, which are precisely the source statuses whose `ValidOrderStatusTransitions` map includes `partially_returned/returned` (`models/order/order.go:40-57`).
- Single-request quantity ceiling (including two items on the same line in one request via the in-loop `returnedQty` increment), ProductID match, negative-refund and over-refund rejection, order-total cap, and the `required,min=0`→`min=0` binding fix are all correct and covered by tests. Sequential double-return is rejected.
- Build (`go build ./...`) PASS; `REDIS_URL= go test -count=1 ./internal/handlers/customer/` PASS including all 8 new tests. Frontend contract holds: the create-response consumer only reads `ret.id` (`frontend/pages/customer/orders/[id].vue:654`), and the client sends `orderItemIdx` as the 0-based index into the order items array (`:622-628`), which matches the `lineByIdx` mapping built at `customer_return.go:102-105`.

### Concrete residual scenario 1 — TOCTOU race on the ceilings (primary)
`customer_return.go:88-98` reads the already-returned tally via `FindByUserID` outside any transaction, and the insert at `customer_return.go:152` is a separate call. There is no row lock, no `SELECT ... FOR UPDATE`, no version guard, and no DB constraint backstopping the ceiling — `ReturnItem` has no unique key on `(OrderID, OrderItemIdx)` and `ReturnRequest` has no per-order unique key (`models/order/return.go:25-60`; the `Create` transaction at `repository/order/return.go:23-46` only wraps the writes). Two concurrent `POST /api/v1/user/orders/:id/returns` for the same order+line both read `remaining = line.Quantity` (each before the other's row is visible), both pass the quantity and `refundTotal <= order.TotalAmount` checks, and both persist. Net effect: a 10-unit line can be claimed twice (20 units), and combined refunds can reach ~2× `order.TotalAmount`. A malicious client needs only to fire parallel requests — no tight timing required, the window spans two DB round-trips. This reproduces the exact H2 impact ("arbitrary quantities / refund fraud", just bounded to ceiling-bypass rather than unbounded), so the fix does not close the vulnerability class.

### Concrete residual scenario 2 — tally undercount past 1000 returns
`customer_return.go:89` uses `FindByUserID(..., 1, 1000)` ordered `created_at DESC`; a user with >1000 non-rejected returns has the oldest claims dropped from the tally, so the remaining-quantity check undercounts and an over-return slips. The fixer's "concerns" section documents this limit but it is not mitigated (no aggregation over all pages, no DB sum).

### Secondary observations (lower severity, not the refutation driver)
- `partially_shipped` orders are return-eligible but the fix checks against ordered quantity, not `ShippedQuantity`/`FulfilledQuantity` (`models/order/order.go:81-82`), so a line that never shipped can still be returned for a refund. Persisted-request integrity only; actual refunds remain admin-gated.
- 403-vs-404 distinction (order exists but not yours → 403; truly missing → 404) lets an authenticated caller probe order-ID existence. Mirrors the existing read path, so not a new leak class.
- The success response body omits `items` (`ret.Items` is not preloaded on the create path); the frontend only reads `ret.id`, so no contract break, but any consumer expecting persisted items in the 201 body would get an empty `items`.

### Suggested hardening (for the fixer to revise)
Perform the remaining-quantity/refund check and the `Create` inside a single transaction against the live DB, or add a DB-level guard — e.g. a partial unique index on `return_items(order_id, order_item_idx)` combined with a `quantity <= ordered - already_committed` invariant enforced in `ReturnRepository.Create`, or an optimistic-lock/`SELECT ... FOR UPDATE` on the order row keyed by `Version` — so the ceiling cannot be raced. For the tally, aggregate over all pages (or sum in SQL) instead of `limit=1000`.

**Files checked:** `backend/internal/handlers/customer/customer_return.go`, `backend/internal/handlers/customer/customer_return_test.go`, `backend/internal/handlers/customer/customer_extensions.go`, `backend/internal/handlers/customer/customer_orders_write_test.go` (fakeOrderRepo), `backend/internal/repository/order/return.go`, `backend/internal/repository/order/order.go`, `backend/internal/services/order/order.go`, `backend/internal/models/order/return.go`, `backend/internal/models/order/order.go`, `backend/internal/services/scopes/userportalscope/services.go`, `backend/internal/pkg/response/response.go`, `frontend/pages/customer/orders/[id].vue`.

## 5. Adversarial review (arguer) — second pass (post-refutation)

**Verdict: CONFIRMED_FIXED** for the H2 class as described, within the single-instance deployment this monolith targets. The two vectors the previous arguer (section 4) used to REFUTE the first pass — the unlocked read-then-write ceiling and the `limit=1000` tally undercount — are now both addressed inside the handler-only owned scope, and I could not construct a credible scenario where the described IDOR/arbitrary-refund bug still manifests, nor a regression of adjacent behavior.

### What I re-verified on disk (not just from the report)
- **IDOR closed:** `customer_return.go:115-118` → 403 when `order.UserID != userID`; `contextUserID(c)` reads the same `c.Get("userID")` as the read path. `TestCustomerCreateReturn_OwnershipForbidden` asserts 403 AND zero persisted rows.
- **Order lookup:** real `OrderRepository.FindByID` (`repository/order/order.go:58-64`) returns `(nil, err)` on missing → 404, no nil-order panic. `Items` is a JSONB column scanned as part of the row (`models/order/order.go:206`), so the `lineByIdx` map is correctly populated in production (not just the fake).
- **Status gate** (`orderStatusAllowsReturn`, lines 22-32) matches exactly the source statuses whose `ValidOrderStatusTransitions` map includes `partially_returned/returned`.
- **TOCTOU now closed within a process:** `returnCreateMu` is held from before `sumReturnedQuantities` (line 136) through `ReturnRepository.Create` (line 206), so the second concurrent request re-reads the tally after the first commit. I confirmed the claim is not a bluff: `TestCustomerCreateReturn_ConcurrentFullClaim` (2 goroutines, full-line claim, `SetMaxOpenConns(1)`) asserts exactly one 201 + one 400 and total persisted qty == 10; it passes deterministically across `-count=3`. Without the mutex this test would fail (both reads see tally=0, both persist).
- **Tally undercount closed:** `sumReturnedQuantities` (lines 50-70) pages all pages at 500/page and fails closed on read error. `TestCustomerCreateReturn_TallyAcrossAllPages` (1001 prior 1-unit claims on a 1001-unit line) returns 400 — the old `limit=1000` read would have accepted it. Passes.
- **Refund/quantity ceilings for a single request are airtight:** per-line qty capped to `min(ordered, max(shipped, fulfilled))`, ProductID must match the line at `OrderItemIdx`, negative refunds and over-line/over-order refund totals rejected; the in-loop `returnedQty[idx] += it.Quantity` correctly handles two entries for the same line in one request. JSON decoder rejects NaN/Inf/overflow floats, so no float-edge bypass of the ceilings.
- **Binding fix is a real fix, not a regression:** `required,min=0` on `orderItemIdx` previously rejected line index 0 — i.e. the frontend's default-selected first line always failed. `min=0` now allows it. Frontend sends `orderItemIdx` as the 0-based array index (`frontend/pages/customer/orders/[id].vue:622-628`), which matches `lineByIdx`.
- **Response shape additive, no contract break:** the only create-response consumer reads `ret.id` (`[id].vue:654`). `ret.Items = items` is additive.
- **Build/tests green:** `go build ./...` PASS; `REDIS_URL= go test ./internal/handlers/customer/ ./internal/models/order/ ./internal/repository/order/` PASS (all 12 create-return tests). `emitLifecycleEvent` under the lock dispatches webhooks/event-bus via goroutines (`safego.Go`), so lock-hold is bounded to fast local DB writes.

### Residual risks (do not refute the H2 fix, but should be tracked)
1. **Multi-instance TOCTOU (documented, real, out of handler scope):** `returnCreateMu` is per-process. If this monolith is ever deployed with >1 replica, the ceiling can still be raced (two instances both read tally=0). The fixer's documentation is accurate — a DB-level guard (partial unique index on `return_items(order_id, order_item_idx)` where status <> 'rejected', `SELECT ... FOR UPDATE`, or a version-guarded insert in `ReturnRepository.Create`) is the correct remediation and is a repository/model change this subagent was forbidden to make. This is the single most important follow-up.
2. **Global per-process mutex is a cross-tenant availability bottleneck (new, introduced by the fix):** a single `returnCreateMu` serializes ALL return creation across all users/orders. The paging loop reads every one of the caller's returns, so a user who has accumulated a large number of returns holds the lock for the full page sweep, blocking every other user's return creation for the duration. Bounded (no network I/O under the lock), and exploiting it requires first legitimately accumulating many returns, but it is a real availability regression worth a per-order lock or a server-side `order_id` filter on the tally query as a follow-up.
3. **Shipped/fulfilled fallback:** when a line records neither `ShippedQuantity` nor `FulfilledQuantity`, claimable falls back to ordered qty (lines 160-167), so a "delivered" order with never-shipped lines can still be returned for full ordered qty. Bounded by ordered qty + refund ceilings, and refunds remain admin-gated — persisted-request integrity only.
4. Minor: 403-vs-404 order-ID probing mirrors the read path (accepted); 404 is also returned on non-not-found lookup errors (cosmetic).

**Bottom line:** the previously-REFUTED concerns are resolved within the allowed scope and proven by tests that would fail without each fix; the described H2 impact is no longer reachable for the single-instance target. The multi-instance ceiling race is a genuine residual that requires the (correctly documented) repository/model-level guard.
