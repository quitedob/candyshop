## 1. Process
Read the current `translation.go` and traced the full call chain (repo → `services/scopes/adminportalscope` → `TranslationService` → `handlers/admin/admin_translations.go`). Before changing signatures I verified the shared-`Statement` premise empirically against the pinned GORM version (v1.30.0): a throwaway test reproducing the exact pre-fix pattern (`r.db.Create/Delete/Delete/Update` and `Clauses(OnConflict).CreateInBatches` on the shared base `*gorm.DB`) showed NO clause leak — `gorm.Open` now returns a base DB with `clone: 1`, so every finisher allocates a fresh `Statement` (GORM `getInstance`, `gorm.go:425`). The ctx/`WithContext` change is still the correct fix for INFO-7 (cancellation/deadline/trace propagation), matches every other repo in the codebase, and is defense-in-depth against the shared-statement footgun.
## 2. Fixes in detail
#### H13 — Translation repo: ctx threading + `WithContext` isolation
- **Problem:** `backend/internal/repository/translation/translation.go:56-115` — `Create`/`Update`/`Delete`/`BulkUpsert` called GORM finishers directly on the shared scoped `*gorm.DB`, with no `context.Context`. The claimed WHERE-clause leak between finishers does NOT reproduce on gorm.io/gorm v1.30.0 (verified empirically: `Delete(1)` then `Delete(2)` deletes both rows; an `Update` after a `Delete` persists; a query after `Clauses(OnConflict).CreateInBatches` is clean), because `gorm.Open` now returns `clone: 1` so each finisher gets a fresh `Statement`. The real, still-valid defect is INFO-7: no ctx on any method, so request cancellation/deadlines/traces never reach these DB calls — inconsistent with every other repository.
- **Fix:** Added `ctx context.Context` as the first parameter to all eight repository methods and start each with `r.db.WithContext(ctx)` (replacing the bare `Session(&gorm.Session{})` in the read methods too, which is subsumed by `WithContext`). Threaded ctx through the `translationRepository` interface and all `TranslationService` methods (`List/GetByID/Create/Update/Delete/Groups/Import/Export`, plus `refreshCache`), and updated `admin_translations.go` to pass `c.Request.Context()` at all 9 call sites.
- **Files:** `backend/internal/repository/translation/translation.go`, `backend/internal/services/translation/translation.go`, `backend/internal/handlers/admin/admin_translations.go`, new `backend/internal/repository/translation/translation_test.go`.
- **Regression test:** `TestDeleteDoesNotLeakWhereClause` seeds 3 rows, calls `Delete(1)` then `Delete(2)` on the same repo, and asserts row 2 is soft-deleted (`gorm.ErrRecordNotFound`) while row 3 survives, and that an `Update` after a `Delete` persists. Uses the repo's in-memory glebarez/sqlite harness (matches `repository/order/coupon_test.go`).

## 4. Adversarial review (arguer)

**Verdict: CONFIRMED_FIXED.** The valid defect (INFO-7: no `context.Context` on any translation repo/service method) is fully and correctly closed, with no regressions found across the entire call chain.

**On the finding's core clause-leak premise (skeptical verification):** I independently confirmed from the pinned gorm.io/gorm v1.30.0 source that the premise does NOT hold. `gorm.Open` returns `&DB{Config: config, clone: 1}` (gorm.go:187) and initializes `db.Statement` exactly once (gorm.go:220, fresh `Clauses: map[string]clause.Clause{}`). Every finisher (`Create`/`Save`/`Delete`/`First`/`Find`/`Count`/`CreateInBatches` — finisher_api.go:24,76,165,404,532) and every chainable method (chainable_api.go:19 et seq.) calls `db.getInstance()` first, and `getInstance()` (gorm.go:425) for `clone == 1` allocates a brand-new `Statement` with an empty `Clauses` map. So a Delete's WHERE id=? cannot leak into a subsequent Delete/Update/query on the shared base DB. The old read methods (`r.db.Session(&gorm.Session{})`) produced `clone: 2`, and `getInstance()` for clone==2 clones the Statement (`tx.Statement = db.Statement.clone()`, gorm.go:444) rather than mutating the shared base, so those reads neither leaked clauses nor wrote to shared state. The base `db.Statement` field is read-only after `Open` (Session only reads the pointer at gorm.go:246; `getInstance` only reads `db.Statement.Context`/`SkipHooks`). Therefore the "concurrent requests race on the same Statement" claim also does not reproduce: no goroutine ever writes the base Statement. The fixer's empirical repro (Delete(1)+Delete(2) both delete; Update-after-Delete persists; OnConflict does not leak) matches the source. I re-ran `REDIS_URL= go test -count=1 ./internal/repository/translation/` — PASS.

**Fix audit (INFO-7 + defense-in-depth):**
- All 8 repo methods now take `ctx` and begin with `r.db.WithContext(ctx)` (translation.go:20,50,58,62,66,70,84,92). `WithContext` subsumes the previous `Session(&gorm.Session{})` (it IS a Session with a context), so the read methods lost nothing.
- The `translationRepository` interface and all `TranslationService` methods (`List/GetByID/Create/Update/Delete/Groups/Import/Export` + `refreshCache`) thread `ctx` end-to-end (services/translation/translation.go).
- All 9 handler call sites pass `c.Request.Context()` (admin_translations.go:30,50,81,106,122,138,148,184,197).
- `ctx` is never nil from any caller: Gin's `c.Request.Context()` and the `Import`→`refreshCache` chain both supply non-nil contexts, so `WithContext`/GORM's `Statement.Context` cannot receive a nil context in practice.
- No missed callers: the only construction sites are `translation.New(db)` (adminportalscope/repositories.go:90) and `translationSvc.NewService(repos.Translation)` (adminportalscope/services.go:111); the only method callers are the admin handler. `SeedTranslations` (database/seed_translations.go:19) and `i18n.Init` (pkg/i18n/i18n.go:22) use their own `*gorm.DB` directly and are untouched.
- Edge cases preserved: `BulkUpsert` empty-slice early return (translation.go:93); Delete-of-missing-id → nil error → handler 200 "deleted" (pre-existing, unchanged); `Save` full-field update semantics (pre-existing); soft-delete filtering via `gorm.DeletedAt` unaffected.

**Regressions:** `go build ./...` PASS (clean); `go vet` on the three changed packages PASS; repo tests PASS; services package compiles (no test files); `REDIS_URL= go test -count=1 ./internal/handlers/admin/` PASS in my run (the fixer's one reported failure in the untracked `admin_role_grant_test.go` did not reproduce and never references translation — it is a parallel-agent artifact against live Postgres, unrelated to this change).

**Minor (non-blocking) observations for the record:** (1) The regression test `TestDeleteDoesNotLeakWhereClause` guards a behavior that does not reproduce on v1.30.0, so it functions as a documentation/defense-in-depth guard rather than a red-green regression test; this is acknowledged honestly in the devlog and is acceptable. (2) The test builds its own SQLite table rather than `AutoMigrate` on the real model, so it could drift from the actual Postgres schema over time — the columns mirror the model today and the test's purpose (Delete/Update isolation) is served.
