**Date:** 2026-08-11
**Source report:** [../../reports/code-review-audit-2026-08-11.md](../../reports/code-review-audit-2026-08-11.md)
**Scope:** backend Go / Gin / GORM
**Trigger:** Bulk/requisition/reorder drafts were created with `Source=""`, never validated compliance/MOQ/credit, confirmed with an empty shipping country (skipping the compliance recheck), and admin order edits wrote client-supplied negative/zero prices verbatim.
**Result:** **FIXED** with regression tests, then **RE-OPENED by the arguer** (admin-edit deadlock on unpriced drafts + credit per-user only) and **RE-FIXED**, then **RE-OPENED again (round 2 refutation)** on two concrete bypasses and **RE-FIXED in round 3**. All targeted tests pass; pre-fix failure of the four new round-3 tests proven by temporary revert.

## 2. Fixes in detail
#### G20(b) — Bulk/requisition/reorder drafts created with Source=""
- **Problem:** `CustomerCreateBulkOrder` (CSV), `CustomerConvertRequisitionToOrder`, and `CustomerReorderFromHistory` built draft orders without setting `Source` (`customer_bulk_order.go`), so `order.Source` defaulted to `""`. The frontend confirm gating keys off the source and downstream logic sees nothing.
- **Fix:** set `Source: modelsOrder.OrderSourceBulk` on all three order constructions (`customer_bulk_order.go:205-215`, `295-305`, `338-349`). Consistent with the confirm path: non-inquiry sources already route through `repriceOrderItems` (server-side catalog/contract re-price), which is exactly what these `UnitPrice=0` drafts need; the H10 negotiated-inquiry branch is unaffected.
#### G20(b) — MOQ never re-enforced at confirm
- **Problem:** draft paths (bulk CSV, requisition, reorder, AI draft) never validated per-product MOQ, and a confirm-time M-19 quantity override can reduce a line below MOQ; `ConfirmAndReserveStockWithFinancials` reserves full quantity with no MOQ guard.
- **Fix:** added `OrderService.ValidateMOQ(items, productsByID)` in `services/order/inventory_rules.go` (aggregates quantity per product, returns violation strings for `qty < product.MOQ`), and `CustomerConfirmOrder` calls it right after the re-price step and returns 422 `min_quantity_not_met` before stock is committed (`customer_orders_write.go`).
#### G20(a) — Confirm rechecks skipped when shipping country is empty
- **Problem:** the confirm-time compliance recheck was gated on `order.ShippingAddress.Country != ""`, so a bulk/requisition/reorder draft (created without an address) sailed past destination-market validation.
- **Fix:** `CustomerConfirmOrder` now (1) rejects a draft that has line items, carries no official compliance evidence, and no shipping country with 422 `target_country_required`, and (2) runs the compliance recheck unconditionally whenever line items exist (the country gate was removed). Evidence-bearing orders (cart/inquiry, validated at intake) are unaffected — the recheck degrades to generic warnings for a missing country, never a false pass on market-restricted products that were validated earlier. This scope was required so the H10 negotiated-pricing tests (items + evidence + no country) keep passing.
#### G20(a) — Credit limit per-order only, never cumulative, never at confirm
- **Problem:** `CheckCompanyCreditLimit` compares only the current order's total against the limit. A buyer could stack several under-limit orders that collectively exceed credit, and bulk/requisition/reorder drafts bypass the check entirely.
- **Fix:** added `OrderService.SumOpenOrderTotalsByUser(ctx, userID, excludeOrderID)` in `services/order/inventory_rules.go` and `Handler.checkCompanyCreditLimitCumulative` in `customer/order_helpers.go`, called at confirm after the total is finalized: `open + thisTotal > limit → 422 credit_limit_exceeded`. Companies without a limit stay unlimited (mirrors `orderpolicy.CheckCompanyCreditLimit`). **Refutation fix:** the open-exposure sum now fails CLOSED — when the company/limit resolve but the sum query errors, the confirm returns 500 `order_confirm_failed` instead of silently lifting the guard (`order_helpers.go`). Company/limit resolution failures still fail open (nothing to enforce, consistent with the per-order check).
#### G20(c) — Admin order edit writes negative/zero prices verbatim
- **Problem:** `AdminUpdateOrder` (`admin_orders_crud.go`) wrote client-supplied `Items[].UnitPrice`, `Subtotal`, `TaxAmount`, `ShippingAmount`, and `TotalAmount` directly, so a negative `TotalAmount` or a zero-price line persisted onto the order and its derived invoice.
- **Fix (round 1):** added `validateAdminOrderPrices` and called it immediately after bind; it rejected any sellable line with `UnitPrice <= 0` and any `TotalAmount <= 0` with a 400.
- **Fix (round 2, refutation):** the round-1 guard conflated the finding's scope — NEGATIVE prices — with the legitimate zero-price state of an unpriced draft, and deadlocked the exact workflow the finding targets. A bulk/requisition/reorder draft is created unpriced (`UnitPrice=0`, `TotalAmount=0`, `Country=""`); the customer cannot confirm it without a destination country (`target_country_required`), and the admin order-edit modal echoes the draft's own zeros, so `AdminUpdateOrder` 400'd every save — including a country-only edit. The draft was simultaneously unconfirmable and uneditable. `validateAdminOrderPrices` now rejects only NEGATIVE values (`UnitPrice < 0`, negative `Subtotal`/`TaxAmount`/`ShippingAmount`, `TotalAmount < 0`) and deliberately allows zero. Draft prices are never authoritative: the customer confirm path re-prices every line server-side, and `AdminCreateOrder` is server-priced, so an unpriced draft cannot reach a confirmed order with zero cost through the customer flow.
#### G20(a) — Contract price-list minimum quantity still bypassed at confirm (refutation edge #4)
- **Problem:** `ValidateMOQ` checks only `product.MOQ`; the contract price-list `MinQuantity` (enforced only at cart creation via `orderpolicy.ValidateLineMinQuantity`) is still bypassed by bulk/requisition/reorder drafts.
- **Fix:** `CustomerConfirmOrder` now resolves the user's contract price list and runs `validateLineMinQuantity` per line for `OrderSourceBulk` drafts right after the MOQ check, returning 422 `min_quantity_not_met` on a below-contract line. Gated on bulk source so the H10 negotiated-inquiry path (a negotiated offer may legitimately sit below a contract tier) and the cart path (already validated at intake) are untouched.
#### G20(a) — Cumulative credit is per-user while the limit is per-company (round-2 refutation basis 1)
- **Problem:** `checkCompanyCreditLimitCumulative` summed only the confirming USER's open orders (`SumOpenOrderTotalsByUser` → `FindByUserID`) but enforced the COMPANY limit. Two buyer users of one company (limit 1000) could each confirm $800 (open_A=0, open_B=0 both pass) leaving $1600 outstanding — the finding's "stack several under-limit orders that collectively exceed credit" harm, still reachable at confirm. No company-scoped open-order sum existed anywhere.
- **Fix:** added `OrderRepository.SumOpenOrderTotalsByCompany(ctx, companyID, excludeOrderID)` in `repository/order/requisition_list.go` — a single SQL aggregate `SUM(total_amount) WHERE status NOT IN (cancelled,returned,expired) AND id <> ? AND user_id IN (SELECT id FROM users WHERE company_id = ?)` with the GORM soft-delete scope. Orders carry only `user_id`, so the company is resolved through `users.company_id` (the Order model has no company column). Exposed via `OrderService.SumOpenOrderTotalsByCompany` in `services/order/inventory_rules.go` using the same interface-extension type-assertion idiom as `ConfirmAndReserveOrderWithFinancials` (the `orderRepository` interface cannot be extended inside owned scope); a repository that cannot scope by company is an ERROR — deliberately fail CLOSED, never a silent fallback to the per-user sum that would re-open the bypass. `checkCompanyCreditLimitCumulative` (`customer/order_helpers.go`) now calls the company sum. The single aggregate also removes the offset-pagination tie hazard for the credit path (no page walk). `SumOpenOrderTotalsByUser` is retained (exported) for callers that genuinely need a single buyer's exposure.
#### G20(a) — M-19 quantity override below price-list min on non-bulk sources (round-2 refutation basis 2)
- **Problem:** the round-2 price-list-min recheck was gated to `OrderSourceBulk`; a CART line validated at intake at qty 100 (≥ min 50) could be confirmed with an M-19 quantity override of 20 — re-priced server-side, MOQ passing if `product.MOQ ≤ 20` — confirming below the contract minimum.
- **Fix:** `CustomerConfirmOrder` now detects M-19 quantity overrides (`overriddenQty`: product IDs whose quantity differs from the draft — a client-added line is always overridden) and extends the price-list-min recheck: bulk drafts still check every line; every other source checks only overridden lines (`filterOverriddenItems`). Unchanged inquiry lines stay excluded (H10 — a negotiated offer may legitimately sit below a contract tier and was settled at intake). Unchanged non-bulk lines stay excluded (validated at intake; re-checking them would add a price lookup per line on every confirm and is outside the finding).
#### G20(b) — Un-gated MOQ recheck rejects below-MOQ negotiated-inquiry (H10) deals (round-2 edge note)
- **Problem:** the round-2 MOQ recheck ran `ValidateMOQ` for EVERY source including `OrderSourceInquiry`; a real negotiated deal with an agreed quantity below `product.MOQ` 422'd `min_quantity_not_met` at confirm (the H10 tests passed only because their products carry `MOQ:0`).
- **Fix:** the MOQ recheck is now gated the same way — inquiry drafts check only M-19-overridden lines (an unchanged negotiated line set is authoritative); all other sources (bulk/requisition/reorder, which never validated MOQ at creation; cart as a defensive recheck) check every line. A below-MOQ negotiated inquiry draft confirms; a customer who actively overrides a quantity below MOQ is still rejected.

A bulk/requisition draft whose lines are below `product.MOQ` can be admin-confirmed directly, so "MOQ is never re-enforced at confirm" remains true on the admin confirm path. The customer confirm path is fixed; the admin path is not, and the devlog does not document a MOQ carve-out for admin confirms (the zero-price carve-out is documented; the MOQ one is not).

### Edge / regression notes
- **M-19 price-list-min override detection is aggregate-by-product**, so a per-line redistribution is missed on non-bulk sources: a cart draft line A qty 100 (≥ min 50) confirmed as two lines A qty 30 + A qty 70 keeps the product aggregate at 100 → `overriddenQty[A]` stays false → `filterOverriddenItems` drops A → the sub-min 30 line is not re-checked (`customer_orders_write.go:544-563,646-659`). MOQ is safe (aggregate), but the per-line contract min is not. Narrow/contrived; a manual API payload, but it is a concrete hole in the new gate.
- **Company sum mixes currencies**: `SUM(total_amount)` across orders of different `currency` is compared to a scalar `company.CreditLimit`; a USD 800 + EUR 800 exposure is summed as 1600. Pre-existing scalar-limit assumption, but the new cumulative check inherits it.
- **Soft-deleted users' open orders are excluded** from the company sum (the `users` subquery carries the soft-delete scope), understating exposure if a departed buyer's confirmed orders remain. Minor.
- **TOCTOU on open-sum+compare** remains (two concurrent confirms/checkouts can both read the pre-commit sum) — acknowledged by the fixer; same shape as the pre-existing per-order check, not a round-3 regression.
