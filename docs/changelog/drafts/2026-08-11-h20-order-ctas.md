# Changelog / Devlog — 2026-08-11 H20 — Quick-order and product-page order requests always fail (missing shipping address)
**Date:** 2026-08-11
**Source report:** [../../reports/code-review-audit-2026-08-11.md](../../reports/code-review-audit-2026-08-11.md)
**Scope:** frontend Nuxt 3 / Vue 3 / TypeScript / Tailwind
**Trigger:** The primary CTAs on the customer quick-order page and the customer product detail page post to `POST /user/orders` without the street/city/country the backend requires, so every submit returned `shipping_street_required` / `shipping_city_required` / `target_country_required` and both flows were dead.
**Result:** Fixed in `frontend/pages/customer/orders/quick.vue` and `frontend/pages/customer/products/[id].vue` (collect + validate the shipping address, prefill from the customer's saved company address, send the full payload); `npm --prefix frontend run typecheck` passes (exit 0).
---
## 1. Process
1. Read both owned pages and traced every submit path: `quick.vue` `submitManualOrder` posted `{ items }` only, and `products/[id].vue` `submitOrderRequest` posted `shippingAddress: { country: ... } as any` (missing street/city) — both hit `POST /user/orders`.
2. Confirmed the backend contract in `backend/internal/handlers/customer/customer_orders_write.go`: `validateCustomerShippingAddress` (line 863) rejects when `shippingAddress.street`, `.city`, or `.country` is empty (`shipping_street_required`, `shipping_city_required`, `target_country_required`); `customerCreateOrderRequest.ShippingAddress` is `modelsOrder.Address{Street,City,State,ZipCode,Country}`.
3. Verified the CSV/requisition/reorder flows in `quick.vue` are unaffected: `CustomerCreateBulkOrder`, `CustomerConvertRequisitionToOrder`, `CustomerReorderFromHistory` (`customer_bulk_order.go`) create `OrderStatusPendingConfirm` drafts with no address validation (only the later confirm step needs a country). So only the two `POST /user/orders` callers needed the fix.
4. Added a shipping-address form + client-side validation + company-address prefill to both pages and re-ran the frontend typecheck.

## 2. Fixes in detail
#### H20(a) — Quick order: manual SKU submit sent no shipping address → always `shipping_street_required`
- **Problem:** `frontend/pages/customer/orders/quick.vue:394` — `submitManualOrder` posted `api.post('/user/orders', { items })` with no `shippingAddress`, so `validateCustomerShippingAddress` rejected every manual quick-order submit.
- **Fix:** Added a "Shipping To" block to the Manual Entry tab (`quick.vue:74-137`) collecting street/city (required), state/zip (optional), all localizable via existing `customer.cart.*` keys; added `shippingAddress` + `shippingErrors` reactive state (`quick.vue:294-295`); added `validateShippingAddress()` (`quick.vue:358-376`, keys `customer.common.shipping_{street,city,country}_required`); `submitManualOrder` now validates first and posts `{ items, incoterms: 'FOB', shippingAddress: { street, city, state, zipCode, country } }` (`quick.vue:384-404`). `loadCompanyAddress()` (`quick.vue:501`) prefills the form from `GET /user/company` `address` on mount (`quick.vue:520`).

#### H20(b) — Product page: "Submit Request" sent only country → always `shipping_street_required`
- **Problem:** `frontend/pages/customer/products/[id].vue:429-448` — `submitOrderRequest` sent `shippingAddress: { country: shippingCountry.value || '' } as any` (the `as any` masked the type error in `useApi.createOrder`, which requires street/city), so street/city were empty and the backend rejected the order.
- **Fix:** Expanded the destination-country row into a shipping-address group collecting street, city, and country (`[id].vue:100-140`); added `shippingStreet`/`shippingCity` refs + `shippingErrors` reactive + `shippingErrorMessage` (`[id].vue:308-312`); added `validateShippingAddress()` (`[id].vue:407`) and `submitOrderRequest` now validates before sending and posts the full `shippingAddress` without the `as any` cast (`[id].vue:430-448`). `loadCompanyAddress()` (`[id].vue:474`) prefills street/city/country from the company address on mount (`[id].vue:490`). `addToCart` behavior is unchanged.
- **Scope note:** all labels/errors reuse existing translation keys (`customer.cart.{shipping_to,street,city,state,zip,country}`, `customer.common.shipping_{street,city,country}_required`, `customer.products.destination_country*`) — present in all 9 locales — so no locale files (outside this task's ownership) were touched.

## 4. Adversarial review (arguer)

**Verdict: CONFIRMED_FIXED.** I attempted to refute the fix and could not construct a credible scenario where the bug still manifests or regresses.

**Root-cause closure for ALL `POST /user/orders` callers.** Audited every caller of the create-order endpoint across the frontend:
- `quick.vue:394 submitManualOrder` — now sends `{ items, incoterms: 'FOB', shippingAddress: { street, city, state, zipCode, country } }` gated by `validateShippingAddress()` (quick.vue:384); payload street/city/country are always non-empty after trim.
- `products/[id].vue:433 submitOrderRequest` — `as any` cast removed; now sends the full address matching `useApi.createOrder`'s required type (useApi.ts:620-631) and is gated by `validateShippingAddress()` ([id].vue:430).
- The other two callers were already correct: `orders/new.vue:455` (`createOrder`) and `orders/new.vue:379` (`createAIAssistOrder`) both use `buildSharedAddressPayload()` which trims and sends street/city/state/zipCode/country. No missed entry point.

**Backend contract cross-checked.** `validateCustomerShippingAddress` (backend/internal/handlers/customer/customer_orders_write.go:863-874) rejects only empty street/city/country (returns `shipping_street_required` / `shipping_city_required` / `target_country_required`); `State`/`ZipCode` are not validated, so `products/[id].vue` sending `state: ''`, `zipCode: ''` is accepted. `Incoterms: 'FOB'` is not whitelist-validated in `CustomerCreateOrder` (it is stored as-is) and matches the platform `default_incoterms` seed (seed_system_settings.go:24) — no rejection risk from the new `incoterms` field on quick.vue.

**Unaffected-flow claim verified.** `customer_bulk_order.go` handlers `CustomerConvertRequisitionToOrder` (line 176), `CustomerCreateBulkOrder` (line 227), `CustomerReorderFromHistory` (line 318) contain no `validateCustomerShippingAddress` call, so the CSV/requisition/reorder tabs correctly needed no address UI. The finding was scoped to the two `POST /user/orders` CTAs only.

**Edge cases.**
- No saved company address (`GET /user/company` errors or `address` null): prefill fails silently, the empty form is caught by client validation on submit — the CTA is now actionable (prompts the buyer) rather than dead. Not a bug.
- Empty/whitespace-only fields: `validateShippingAddress()` trims and requires non-empty street/city/country on both pages, so the backend can never receive a blank required field from these flows.
- `r.quantity!` non-null assertion in quick.vue:379 is safe — `validManualRows` filters `(r.quantity ?? 0) > 0`.
- Client uses `customer.common.shipping_country_required` while the backend error key is `target_country_required` — different text on failure, cosmetic only, no functional impact.
- Mild redundancy on the products page when all fields are empty (per-field errors + combined `shippingErrorMessage`) — acknowledged by the fixer, not a defect.

**i18n.** All reused keys exist in all 9 locales (en, zh, ja, ko, ar, id, ms, th, vi): `customer.cart.{shipping_to,street,city,state,zip,country}`, `customer.common.shipping_{street,city,country}_required`, `customer.products.destination_country(_placeholder)`. Verified by grep across `frontend/i18n/*/customer.json`. No missing-key fallback risk.

**Typecheck.** `NODE_ENV=development npm --prefix frontend run typecheck` exits 2, but ALL 5 errors are in `pages/admin/inventory/index.vue` (TS2339 `displayPagination` on the `useI18n` return) — an unrelated in-flight edit outside this fixer's ownership (zero errors in `quick.vue` or `products/[id].vue`). Per the arbitration rule, the fixer's files are clean; the inventory failure is attributed to the concurrent admin-pagination refactor and should be resolved by that owner, not this fix.

**Regressions checked.** `addToCart` on the products page is unchanged (different endpoint). Button disable/enable logic unchanged apart from the new `submitting` gating. The products page submit payload otherwise matches its pre-fix shape (`unitPrice: displayPrice`, `specifications: selectedVariant.sku`). No regression on non-affected paths.
