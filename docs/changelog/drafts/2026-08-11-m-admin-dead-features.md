# Changelog / Devlog — 2026-08-11 M4 Admin UI dead features (HITL approve/reject, Stop, inventory filters, template, orders edit/refund, content double-submit)

**Date:** 2026-08-11
**Source report:** [../../reports/code-review-audit-2026-08-11.md](../../reports/code-review-audit-2026-08-11.md)
**Scope:** frontend Nuxt 3 / Vue 3 / TypeScript / Tailwind
**Trigger:** M4 — seven admin UI controls were dead or wrong against the real backend contract: HITL Approve/Reject sent a literal string into a fresh SSE stream (Reject was local-only); the Stop button was disabled exactly while streaming; inventory filters ran client-side over the current server page only; the import template downloaded as `.csv` while the importer only accepts `.xlsx`; editing an order dropped `fulfilledQuantity`/`shippedQuantity`; cancelling a paid order never sent `refund:true` (blocked by the backend); and the content Save button double-submitted.
**Result:** All seven fixed against the verified backend endpoints; `npm --prefix frontend run typecheck` clean.
---
## 1. Process

Read the current content of all five owned files (they carry other agents' in-flight edits — ai/index.vue, content/index.vue, inventory/index.vue were modified this session). Traced the real backend contracts the UI must satisfy: the quotation HITL queue (`GET/POST /admin/quotation-reviews`, `admin_quotation_reviews.go`), the refund-blocked cancel path (`admin_orders.go` `AdminUpdateOrderStatus`, `refund bool`), the `.xlsx`-only importer (`admin_inventory_xlsx.go` extension guard), the order-edit items contract (`admin_orders_crud.go` `*[]modelsOrder.OrderItem`), and the `/admin/inventory` endpoint (which takes NO filter query params — confirmed `AdminGetInventory` calls `GetProductsFiltered(..., "", "", 0, 0)`). Matched surrounding style (i18n via `t()`, existing keys only — no new keys were added since translations are DB-backed), and re-used the repo's `useSubmitGuard` composable for the double-submit guard.

## 2. Fixes in detail

#### M4(a) — HITL Approve/Reject wired to the real quotation-review endpoints
- **Problem:** `frontend/pages/admin/ai/index.vue` `approveAction()` did `sendMessage(\`${t('admin.ai.approve')}: ${action.label}\`)` — a literal string into a brand-new SSE stream; `rejectAction()` only dropped the entry locally. The SSE `action/interrupted` events come from the Eino review-and-edit wrapper (`backend/internal/pkg/eino/tool/review_edit.go`), which the SSE flow (`handlers/system/sse_handler.go`) can never resume (fresh runner per request, in-memory checkpoint store), so both buttons were dead UI.
- **Fix:** The "Pending Approvals" panel now sources the persisted HITL queue the backend actually supports — `GET /admin/quotation-reviews?status=pending` (id, customerRef, currency, totalAmount, strategyNotes) via `fetchPendingApprovals()` (mounted + a manual refresh button). `approveAction`/`rejectAction` now call `POST /admin/quotation-reviews/:id/approve` and `/reject` (idempotent `api.post`, guarded by a `hitlBusy` flag), and SSE `interrupted` events are surfaced as an informational note in the chat transcript instead of dead UI. (`ai/index.vue:559-633`, `:113-146`)

#### M4(b) — Stop button enabled while streaming
- **Problem:** `ai/index.vue:100` — the submit/Stop button was `:disabled="!input.trim() || isStreaming"`, i.e. disabled exactly when a stream is running and Stop is needed. `handleSubmit` already aborted via `abortController`, but the button could never be clicked.
- **Fix:** `:disabled="!isStreaming && !input.trim()"` — while streaming the button is enabled and shows Stop, clicking aborts the SSE and appends `admin.ai.stream_stopped`. (`ai/index.vue:98-106`, `handleSubmit` unchanged)

#### M4(c) — Inventory filters page-correct (full-dataset client filter)
- **Problem:** `frontend/pages/admin/inventory/index.vue` `filteredItems` filtered `items.value`, which only holds the current server page (20 rows), so search/stock/category silently missed every other page. The backend `/admin/inventory` (`admin_inventory.go:22-39`) accepts NO filter params (`GetProductsFiltered(..., "", "", 0, 0)`), so server-side filtering is not available.
- **Fix:** When any filter is active, the page now loads the full inventory (paged requests at `limit:100`, cached per session, invalidated after adjustments/batch edits/imports and when leaving filter mode) and filters + paginates locally via `matchesFilters`/`filteredFull`/`filteredItems`/`displayPagination`; the footer pagination and the stat cards read `displayPagination` so totals match the filtered set. Unfiltered mode keeps the original server-side pagination. (`inventory/index.vue:711-724`, `799-838`, `964-997`, `1174-1190`)

#### M4(d) — Import template is a real .xlsx
- **Problem:** `downloadTemplate()` produced a `.csv` blob named `inventory_import_template.csv`, but the importer (`backend/internal/handlers/admin/admin_inventory_xlsx.go:246`) rejects non-`.xlsx` by extension before excelize opens it — the template could never be imported.
- **Fix:** Generate a minimal but valid OOXML `.xlsx` client-side (no spreadsheet lib is bundled): a stored (uncompressed) ZIP of the standard parts (`[Content_Types].xml`, `_rels/.rels`, `xl/workbook.xml`, `xl/_rels/workbook.xml.rels`, `xl/worksheets/sheet1.xml` with inline strings), via `crc32`/`buildXlsxZip`/`buildInventoryTemplateXlsx`. Downloaded as `inventory_import_template.xlsx`. Independently verified by reproducing the generator in Node and opening the output with excelize v2.10.1 (the backend's importer lib): reads sheet "Inventory", 2 rows, 22 columns. (`inventory/index.vue:1034-1215`)

#### M4(e) — Order edit preserves fulfilled/shippedQuantity
- **Problem:** `frontend/pages/admin/orders/index.vue` `fillForm`/`buildPayload` mapped items to `{ productId, quantity, unitPrice, specifications }`, dropping `fulfilledQuantity`/`shippedQuantity`. `AdminUpdateOrder` (`admin_orders_crud.go:281-283`) replaces `order.Items` wholesale when `req.Items != nil`, so editing a partially-fulfilled order zeroed the fulfillment progress → downstream fulfillment bookkeeping broke (422).
- **Fix:** The item type, `fillForm`, and `buildPayload` now carry `fulfilledQuantity`/`shippedQuantity` through the edit payload (zero for new lines, real values for existing). (`orders/index.vue:397`, `:475-477`, `:518-529`)

#### M4(f) — Cancelling a paid order sends `refund:true`
- **Problem:** `frontend/pages/admin/orders/[id].vue` `updateStatus()` sent only `{ status, trackingNumber? }`. The backend `AdminUpdateOrderStatus` (`admin_orders.go:171-202`) BLOCKS cancelling an order with confirmed payments (`422 order_cancel_requires_refund`) unless `refund:true` is sent — so cancelling a paid order was impossible from the UI.
- **Fix:** When the target status is `cancelled` and the order's paymentStatus is `paid`/`partial`, `updateStatus` confirms with the admin (reuses localized `admin.orders.confirm_refund`) and then includes `refund: true`, authorising the backend to refund confirmed payments. Unpaid cancels are unchanged. (`orders/[id].vue:637-650`)

#### M4(g) — Content Save double-submit guarded
- **Problem:** `frontend/pages/admin/content/index.vue` `saveContent()` could fire twice on a fast double-click (the `saving` ref disables the button but the handler had no in-flight short-circuit), creating/updating the content twice.
- **Fix:** Wrapped the save body in `useSubmitGuard().guard(...)` (repo composable, short-circuits concurrent invocations); the inner try/catch keeps the localized error UI and `saving` flag. (`content/index.vue:225`, `:665-694`)

## 4. Adversarial review (arguer)

**Verdict: CONFIRMED_FIXED** (all seven M4 dead-feature findings are closed against the real backend contracts; no residual reproduction or regression found).

Audit performed: re-read all five owned files on disk, traced every claimed backend contract, re-ran `npm --prefix frontend run typecheck` (EXIT=0, zero `error TS`), and independently reproduced the template generator.

Per-finding checks:

- **M4(a) HITL — CONFIRMED.** `approveAction`/`rejectAction` (ai/index.vue:606-626) now `api.post` to `/admin/quotation-reviews/:id/{approve,reject}` (routes adminportal/register.go:168-170; `decideQuotationReview` tolerates the `{}` body via ignored `ShouldBindJSON`). The panel loads `GET /admin/quotation-reviews?status=pending`; `QuotationReviewRepository.List` filters `status = ?` (repository/trade/quotation_review.go:32-36) and the model exposes `customerRef/currency/totalAmount/strategyNotes/suggestedDiscountPct` matching the mapping. The queue is genuinely populated: `submit_quotation_for_human_review` is registered in BOTH `agent.go:67` and `deep_b2b.go:69` with a real `SaveQuotationReview` saver. Grep confirms no literal-string-into-SSE path survives anywhere in the frontend. The remaining `action/interrupted` branch (ai/index.vue:559-575) is a transcript note, not dead UI. Documented semantic change (in-session `review_edit` interrupts are no longer actionable items) is defensible — they were unresolvable before (fresh SSE runner per request).
- **M4(b) Stop — CONFIRMED.** `:disabled="!isStreaming && !input.trim()"` (ai/index.vue:100) enables the Stop affordance exactly while streaming; `handleSubmit` (431-440) aborts via `abortController` and `sendMessage`'s AbortError branch appends `stream_stopped`. No way to click a disabled Stop anymore.
- **M4(c) Inventory filters — CONFIRMED.** The endpoint truly takes no filter params (`AdminGetInventory` → `GetProductsFiltered(..., "", "", 0, 0)`), so the full-dataset client-filter approach is the right call. Filtered path reads `allInventory` (paged at limit:100, cached, invalidated on adjustments/batch/import/clear), `filteredFull`/`filteredItems`/`displayPagination` slice+page locally, stats read `filteredFull`, and the filter-change watch resets to page 1. Unfiltered path keeps server pagination verbatim. `res.pagination.totalPages` matches `PaginatedResponse.Pagination` JSON (`data`/`pagination.totalPages`), already relied on by the pre-existing footer. **Edge (not a refutation):** the 50-page cap (≈5000 SKUs) still leaves filtering page-incomplete for larger catalogs; documented and strictly better than the prior current-page-only behaviour.
- **M4(d) Template — CONFIRMED.** Independently reproduced `crc32`/`buildXlsxZip`/`buildInventoryTemplateXlsx` verbatim in Node (4607-byte file) and opened it with excelize v2.10.1 (the backend's importer lib): `GetSheetList()=[Inventory]`, `GetSheetName(0)=Inventory`, `GetRows` → 2 rows, 22 columns, all 22 headers hit `knownProductFields` (mapColumnsHeuristic), example row parses (`0.50`→ParseFloat, `1000`/`5000`→Atoi, `active`→IsValidProductStatus). Backend extension guard (`admin_inventory_xlsx.go:246`) and content-type allowlist (Blob type is the official OOXML mime) both pass. Note: the example row would import "Example Candy" if the admin uploads the template unchanged — standard template behaviour, visible in the preview UI.
- **M4(e) Order edit — CONFIRMED.** `AdminUpdateOrder` replaces `order.Items` wholesale when `req.Items != nil` (admin_orders_crud.go:281-283), and `OrderItem` carries `json:"fulfilledQuantity,omitempty"`/`json:"shippedQuantity,omitempty"` (order.go:81-82), so preserving the fields in `fillForm`/`buildPayload` (orders/index.vue:476, 526-527) prevents zeroing fulfillment progress. `omitempty` only affects marshaling, not the unmarshal of the edit payload; new lines default to 0. Create path is unaffected (0s harmless).
- **M4(f) Cancel refund — CONFIRMED.** Backend blocks cancellation with confirmed payment records unless `refund:true` (`admin_orders.go:171-202`, `order_cancel_requires_refund`); the fix sends `refund: true` when target is `cancelled` and `isPaidOrPartial(paymentStatus)` after `confirm` (orders/[id].vue:637-650). Sending `refund:true` when no confirmed records exist is harmless (count==0 branch skips). `admin.orders.confirm_refund` resolves in all 9 frontend locale files (pre-existing key, re-used). **Edge (data-integrity, not the fix):** if paymentStatus says `unpaid` but confirmed payment records exist, the UI still won't send refund:true and cancel stays blocked with an informative 422 detail.
- **M4(g) Content double-submit — CONFIRMED.** `saveContent` is wrapped in `submitGuard.guard(...)` (content/index.vue:670); `useSubmitGuard.guard` flips `submitting` synchronously so a second concurrent invocation short-circuits to `undefined` before the closure runs (the `saving`-disabled button alone was racy). The inner try/catch preserves the localized error UI; the guard's re-throw never fires because the closure swallows errors. The separate drawer publish path `publishAiContent` already short-circuits via `aiPublishing`. No regression: `admin.orders.confirm_refund`/`admin.ai.pending_approvals`/`admin.ai.no_pending_approvals` all exist in every frontend locale.

Typecheck is clean (zero `error TS`); no failures attributable to these files. The three residual notes (5000-SKU filter cap, HITL panel semantic shift, cancel-refund paymentStatus/record inconsistency) are documented edges, not manifestations of the original dead-feature bugs.
