# Changelog / Devlog — 2026-08-11 H19 Invoice create always 400 (totalAmount vs required amount)
**Date:** 2026-08-11
**Source report:** [../../reports/code-review-audit-2026-08-11.md](../../reports/code-review-audit-2026-08-11.md)
**Scope:** frontend Nuxt 3 / Vue 3 / TypeScript / Tailwind
**Trigger:** Admin invoice create always returned 400 because the payload sent `totalAmount` while the backend create request binds a required `amount` field.
**Result:** `saveInvoice` now maps `totalAmount → amount` on CREATE only, drops backend-ignored/UI-only fields, normalizes `dueDate` to RFC3339 (a second latent 400 cause). The EDIT (PUT) path no longer sends `amount` at all — the update binds `amount` as the PRE-TAX `Amount` and recomputes `TotalAmount = Amount + TaxAmount + freight`, so sending the tax/shipping-inclusive `totalAmount` inflated the total on every save (round-2 regression found by the arguer); omitting it on edit restores the pre-fix behavior (edits never mutated the amount). Round 3 (arguer refutation): the `min="0.01" required` added in round 2 was applied to the SHARED create/edit totalAmount input and, on edit, blocked native form submission for zero-total draft invoices — a functional edit blocker, not cosmetic. Now scoped to create only: `:min="editingId ? undefined : 0.01" :required="!editingId"`, so create still rejects amount=0 while $0-total drafts remain fully editable. `npm --prefix frontend run typecheck` from repo root: EXIT=0, zero errors.

## 2. Fixes in detail
#### H19 — Align invoice CREATE payload with the backend binding; stop sending `amount` on edit
- **Problem:** (create) `frontend/pages/admin/invoices/index.vue` `saveInvoice` sent `totalAmount`, `status` and `invoiceNo`, none of which exist on the backend `adminCreateInvoiceRequest` (`backend/internal/handlers/admin/admin_invoices.go:63` binds `amount` with `binding:"required"`). Gin ignored the unknown fields, so `amount` was always missing → every create 400'd. Additionally the `<input type="date">` dueDate value is `YYYY-MM-DD`, but the handler parses dueDate with `time.Parse(time.RFC3339, ...)` (`parseOptionalNullableTime`, admin_invoices.go:245-254), so create would 400 on dueDate even after the amount was fixed.
- **Problem:** (edit, introduced by round 1) Applying the same `amount: totalAmount` mapping on PUT is a regression. The update binds `amount` as the PRE-TAX `Amount` (admin_invoices.go:130-159) and `ValidateAndPersistInvoiceUpdate` recomputes `after.TotalAmount = after.Amount + after.TaxAmount + freight` with `freight = before.TotalAmount - before.Amount - before.TaxAmount` (invoice_policy.go:136-140). But `form.totalAmount` is loaded from the tax/shipping-inclusive backend `totalAmount` (index.vue:484). Concrete: order-derived invoice Amount=1000, TaxAmount=50, ShippingAmount=50, TotalAmount=1100; user opens Edit, changes nothing, Save → payload.amount=1100 → after.Amount=1100 → after.TotalAmount=1200. Silent +100 inflation, persisted because a linked DRAFT skips the adjustment-reason 422 gate (invoice_policy.go:143). Pre-fix edits never sent `amount` (the update struct has no `totalAmount` key, so it was ignored), so this was newly introduced by the round-1 fix.
- **Fix:** `saveInvoice` now builds a single `basePayload` (`{ ...rest, dueDate: toRfc3339(form.dueDate) ?? '' }`) and only the CREATE branch adds `{ amount: totalAmount }`; the PUT branch sends `basePayload` without `amount`, preserving the pre-fix edit behavior (amount never mutated) with no inflation. Added `toRfc3339` helper re-encoding `YYYY-MM-DD` to `YYYY-MM-DDT00:00:00Z` (passes through existing RFC3339, empty → `''` so the backend's "no due date"/clear semantics are preserved).
- **Problem:** (round 3, introduced by round 2) `min="0.01" required` was added to the single totalAmount input rendered by BOTH the create and edit modals (index.vue:191). Create needs it (backend `binding:"required"` rejects amount=0), but on edit it is a hard native-validation gate: any 0/empty value blocks the submit event, so `@submit.prevent="saveInvoice"` never runs. A $0-total DRAFT — from-order on a zero-total order (admin order CRUD has no positive-total guard; `order.Subtotal = *req.Subtotal` accepted at admin_orders_crud.go:285) or any legacy row `normalizeInvoice` maps to 0 — becomes completely un-editable (cannot change notes/dueDate/currency). Pre-fix, the same edit submitted fine. Functional blocker, not cosmetic.
- **Fix:** (round 3) scoped the constraint to create only, per the arguer's one-line suggestion: `:min="editingId ? undefined : 0.01" :required="!editingId"`. Create (`editingId === ''`) keeps `min="0.01"` + `required`, so amount=0 is still rejected in the browser before reaching the backend; edit (`editingId` set) binds neither, so $0-total drafts submit normally — and since the PUT branch omits `amount`, the backend is unaffected.

## 4. Adversarial review (arguer) — Round 3 (review of the round-3 fix)

**Verdict: CONFIRMED_FIXED.** I attempted to refute the round-3 fix and could not construct a credible scenario where the H19 create-400 still manifests, where the round-1 edit-inflation regression resurfaces, or where the round-3 edit-blocker fix introduces a new regression. All three verified against current on-disk code and the backend handlers; typecheck passes EXIT=0.

**Create path — fixed, re-verified on disk.**
- `frontend/pages/admin/invoices/index.vue:524` still sends `{ ...basePayload, amount: totalAmount }`; `totalAmount` is destructured from `form` (line 516) as a number. `adminCreateInvoiceRequest.Amount` is `float64 binding:"required"` (admin_invoices.go:67) — satisfied for any non-zero value. `dueDate` is RFC3339-normalized by `toRfc3339` (line 534) so `parseOptionalNullableTime` (admin_invoices.go:245-254) accepts it; `''` → nil. No residual 400 for valid input. The grep confirms `index.vue:524` is the ONLY invoice-create POST in the frontend (customer portal invoices are read-only GETs; the customer negotiation `totalAmount` at `customer/inquiries/[id].vue:268` is a different feature, offers, not invoice creation).
- The `min="0.01" required` create guard is preserved: on create `editingId === ''` → `:min="0.01" :required="true"` (line 191), so amount=0/empty never reaches the backend. `openCreateModal` resets `editingId.value = ''` (line 475) before showing the modal, so there is no stale-id path into the create form.

**Edit inflation (round-1 regression) — stays fixed.**
- The PUT branch (line 522) sends `basePayload` without `amount`. `ValidateAndPersistInvoiceUpdate` recomputes `after.TotalAmount = after.Amount + after.TaxAmount + freight`, `freight = before.TotalAmount - before.Amount - before.TaxAmount` (invoice_policy.go:136-140). With `amount`/`taxAmount` absent from the PUT, `after.Amount`/`after.TaxAmount` are unchanged → `freight` unchanged → `after.TotalAmount` recomputes identically. No inflation.

**Round-3 edit blocker ($0-total drafts) — fixed.**
- `:min="editingId ? undefined : 0.01" :required="!editingId"` at line 191: on edit `editingId` is truthy → both attributes absent (Vue renders no `min`/`required` for `undefined`/`false`), so a $0-total draft (from-order on a zero-total order, or any legacy `normalizeInvoice`-to-0 row) opens, Save fires `saveInvoice`, and the PUT omits `amount` — the backend is unaffected. No other field on the edit form carries native `required`/`min`/`max`, so nothing else blocks submit. `editingId` is a top-level `ref('')` auto-unwrapped in template scope; even a numeric-string id like `"0"` is truthy, so the edit branch is correct.

**Edge cases examined — none reintroduce H19 or a new regression.**
- `amount=0` create → blocked in UI by create-only min/required; backend `binding:"required"` would reject it anyway. Not H19.
- dueDate: edit loads `isoDatePrefix(invoice.dueDate)`; `toRfc3339('')` → `''` → nil (clear/no-date preserved). A stored dueDate with a non-midnight time is normalized to `T00:00:00Z` on save — introduced by round 1, but strictly an improvement: pre-fix the edit path sent raw `YYYY-MM-DD`, which `parseOptionalNullableTime` rejected with 400, so editing any invoice with a set dueDate was broken before. Not a regression.
- `notes=''` on edit cannot clear a stored note (backend guard `req.Notes == "" && len(query) > 0`, admin_invoices.go:165) — pre-existing backend behavior, unrelated to H19, unchanged by this fix.
- PUT sends `type`/`orderId`, which the update request struct does not bind; Gin ignores unknown JSON keys (no `DisallowUnknownFields`). Harmless.
- Edit-modal totalAmount/paidAmount/invoiceDate/status remain silent no-ops on save — pre-existing (the update request never bound those keys) and unchanged since round 2; not a new regression.

## Round 2 response (fixer) — addressing the refutation

**Admitted and fixed.** The arguer's edit-path regression is mechanically correct and was a genuine defect introduced by the round-1 fix. `saveInvoice` previously applied `amount: totalAmount` on BOTH POST and PUT; because `openEditModal` populates `form.totalAmount` from the tax/shipping-inclusive backend `totalAmount` while `AdminUpdateInvoice` binds `amount` as the pre-tax `Amount` and recomputes `after.TotalAmount = after.Amount + after.TaxAmount + freight` (invoice_policy.go:136-140), a no-op Save on an order-derived draft (Amount=1000, Tax=50, Shipping=50, Total=1100) sent amount=1100 → after.TotalAmount=1200 — silent +100 inflation, persisted because a linked draft skips the 422 adjustment-reason gate.

**Resolution adopted:** the arguer's primary recommendation (first option). The PUT branch now sends `basePayload` WITHOUT `amount` — `amount` is sent only on POST. This restores the exact pre-fix edit behavior (edits never mutated the amount; the update struct never bound `totalAmount` anyway), so no inflation and no new 422-gate trigger. Options 2 (add `taxAmount` to the form) and 3 were considered but are out of scope for H19 and would either require a form redesign or send the tax-inclusive value into a pre-tax field, which is exactly the bug being fixed.

**Verify the arguer's concrete scenario is now closed:** open Edit on derived Amount=1000/Tax=50/Shipping=50/Total=1100, change nothing, Save → PUT payload = `{ orderId, type, currency, dueDate, notes }` (no `amount`) → `after.Amount` stays 1000, `after.TaxAmount` stays 50, `freight` stays 50 → `after.TotalAmount` = 1000+50+50 = 1100. No change, no inflation.

**Remaining acknowledged-but-non-blocking items (all unchanged by round 2):**
- `min="0.01"` blocks zeroing an amount during edit — the amount field is a no-op on edit now anyway, so this is purely cosmetic; matches create semantics. Not a regression.
- Non-draft linked financial edit → 422 `adjustment_reason_required` with no reason field in the modal — pre-existing (reachable via currency edit before H19), not introduced by this fix.
- `amount=0` on create still 400s at the backend — correctly blocked in the UI by `min="0.01" required`; not the H19 bug.

## Round 3 response (fixer) — addressing the round-3 refutation

**Admitted: the arguer is correct, and my round-2 characterization was wrong.** `min="0.01" required` on the single totalAmount input shared by the create and edit modals (index.vue:191) is a functional edit blocker, not cosmetic. Native browser constraint validation runs before `submit` fires, so any 0/empty value on the field stops `@submit.prevent="saveInvoice"` entirely. The reachable scenario is real: (1) admin order CRUD accepts a zero-total order (`order.Subtotal = *req.Subtotal`, admin_orders_crud.go:285, no positive guard); (2) "Create from order" derives a DRAFT with TotalAmount=0+0+0=0 (invoice_policy.go:90-102); (3) Edit → `form.totalAmount = invoice.totalAmount || 0 = 0` (index.vue:484); (4) Save blocked by `required min="0.01"` → the $0 draft becomes un-editable. The same blocker hits any legacy 0/absent-total row. Pre-fix, that edit submitted fine. Round 2's "purely cosmetic" claim is withdrawn.

**Fix adopted (the arguer's one-line suggestion):** scoped the constraint to create only —
`:min="editingId ? undefined : 0.01" :required="!editingId"` at index.vue:191.
- Create (`editingId === ''`): `min="0.01"` + `required` → amount=0/empty still rejected in the browser before reaching the backend. The H19 create-400 fix and its `amount=0` guard are preserved.
- Edit (`editingId` truthy): both attributes are absent → a $0-total draft opens and Save submits normally. Since the PUT branch omits `amount`, the backend is unaffected — no inflation, no 422 gate trigger.

**Walk the arguer's concrete scenario:** $0 draft → Edit → Save now runs `saveInvoice` → PUT sends `{ orderId, type, currency, dueDate, notes }` (no `amount`) → `after.Amount`/`after.TaxAmount`/`freight` unchanged → invoice is editable (notes/dueDate/currency) exactly as pre-fix.

**Re-verified create path is unchanged:** POST still sends `{ orderId, type, currency, notes, dueDate: toRfc3339(form.dueDate) ?? '', amount: totalAmount }` — `amount` satisfies `binding:"required"`; dueDate RFC3339-normalized; `''` → nil. Non-zero amount → 201.

**Edge cases 2-5 from the arguer (all acknowledged, none introduced by this round):**
- (2) amount=0 create → backend 400 — still correctly blocked in UI by create-only min/required; not the H19 bug.
- (3) Non-draft linked financial edit → 422 `adjustment_reason_required`, no reason field in modal — pre-existing (currency edit reaches it pre-H19); not broadened since `amount` is no longer sent on edit.
- (4) Edit modal status/invoiceNumber/paidAmount/invoiceDate/totalAmount remain silent no-ops on save — pre-existing; backend update never bound those keys.
- (5) `toRfc3339` passthrough branch effectively dead (date inputs emit YYYY-MM-DD) but harmless; empty dueDate → nil on both create and edit.

**Typecheck:** `npm --prefix frontend run typecheck` from repo root → EXIT=0, zero errors; owned file `frontend/pages/admin/invoices/index.vue` clean. The round-2 report's flagged unrelated inventory error is gone on re-run (parallel agent's `buildXlsxZip` now returns `Uint8Array<ArrayBuffer>`); the stale note is updated in the verification table above.
