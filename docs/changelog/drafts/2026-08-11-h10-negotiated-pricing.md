# Changelog / Devlog — 2026-08-11 H10 Negotiated Pricing Dead Data
**Date:** 2026-08-11
**Source report:** [../../reports/code-review-audit-2026-08-11.md](../../reports/code-review-audit-2026-08-11.md)
**Scope:** backend Go / Gin / GORM
**Trigger:** Negotiated offer unit prices were applied only to single-line inquiries (`len(items)==1` guard), so multi-line negotiated orders persisted catalog/BasePrice on their lines and the negotiated terms never reached the order lines. Even when intake did persist the negotiated price, `CustomerConfirmOrder` re-priced every line from the catalog / contract price list at confirm, clobbering the agreed total and 422-ing BasePrice=0 OEM-only offers.
**Result:** CLOSED. Four passes closed the full negotiated-pricing chain end-to-end, including the billing document. (1) The intake half — the accepted offer's unit price now reaches EVERY order line via `effectiveUnitPrice`, with `Source=inquiry` marker. (2) The confirm-price guard — a `Source == OrderSourceInquiry` branch preserves the server-authoritative draft unit prices instead of re-pricing from the catalog / contract price list. (3) The confirm-TOTAL guard — an inquiry draft's authoritative `order.TotalAmount` (the intake contract amount) is preserved as the confirmed total whenever the confirm line set matches the draft and the total is non-zero, so a deal-level negotiated total that does NOT equal `sum(unit×qty)` (round-number / discounted offer) survives confirm, and the confirmed order agrees with the trade built at intake from `order.TotalAmount`. (4) The invoice-agreement guard (this round) — the confirmed order is now internally consistent: the negotiated lines are rescaled to the negotiated total (`scaleInquiryLinesToTotal`) so `Subtotal == TotalAmount == negotiated total` (tax/shipping stay 0), restoring the `TotalAmount == Subtotal + Tax + Shipping` invariant the invoice-derivation path relies on. `CreateInvoiceFromOrder` (`Amount = Subtotal`, `TotalAmount = Subtotal + Tax + Shipping`) therefore bills the negotiated total, closing the arguer's invoice over-billing regression (a discounted deal is no longer billed at the 2500 line-price sum). The confirmed order, the derived invoice, the payment amount (`order.TotalAmount`) and the intake trade all agree. All four passes are covered by regression tests that fail on the pre-fix path and pass post-fix. Full build + targeted tests + vet pass. Status: DONE.

## 2. Fixes in detail
#### H10 — Negotiated pricing is dead data; confirm re-prices from catalog
- **Problem:** `backend/internal/services/orderintake/intake.go:182-184` (pre-fix) applied `offer.UnitPrice` to the order lines only when `len(items) == 1`. For multi-line inquiries the negotiated unit price was silently dropped and every line kept the catalog/`BasePrice` resolved by `resolveUnitPrice` (which also passes an empty priceListID, so contract-price lists are never consulted on this path). The draft's `TotalAmount` was set to `offer.TotalAmount`, but the persisted lines carried catalog prices, so trade documents and the confirm-time totals disagreed with the accepted offer.
- **Fix:** `backend/internal/services/orderintake/intake.go:170` — per-line pricing now goes through a new pure helper `effectiveUnitPrice(catalogPrice, offer)` (`intake.go:263-271`) which returns `offer.UnitPrice` when the offer carries one (applies to every matching line) and falls back to the resolved catalog/contract price otherwise. The `len(items)==1` special case is removed entirely. The existing totals block (`intake.go:205-208`) already keeps `offer.TotalAmount` authoritative for negotiated orders, and `subtotal` now reflects the negotiated line prices. `Source` is set to `OrderSourceInquiry` (`intake.go:228`), which is the marker a confirm-path guard branches on. No models were changed (outside scope). No caller signature changed (`customer_negotiation.go:156`, `admin_negotiation.go:112`, `admin_inquiry_convert.go:58` still compile; nil-offer path keeps catalog prices).
- **Known residual (NOT addressed by this change — outside owned file, refuted by arguer):** `CustomerConfirmOrder` (`backend/internal/handlers/customer/customer_orders_write.go:518`) calls `repriceOrderItems` unconditionally; `repriceOrderItems` (`backend/internal/handlers/customer/checkout_pricing.go:87-161`) recomputes every line from the contract price list (:144-147) / `BasePrice` (:149-151) / checkout cost-stack (:155) / channel multiplier (:156) with no `Source == inquiry` or negotiated guard, then :557-558 rebuild subtotal/total and :577 persists over the negotiated total. Even single-line negotiated orders are clobbered at confirm; OEM-only offers (BasePrice 0) hit `errRepriceNoPrice` (:152-154) → 422 `no_price`, making a validly-priced negotiated order unconfirmable.
- **Test:** `backend/internal/services/orderintake/intake_negotiated_test.go` — `TestEffectiveUnitPrice` (5 cases incl. negotiated-wins and zero-price fallbacks) plus three `CreateOrderFromAcceptedOffer` integration tests using fake `productRepository` / `priceRepository` / `orderRepository`: multi-line negotiated offer applies 2.5 to every line with TotalAmount=500 and Subtotal=500; single-line negotiated preserves prior behavior on the draft; no-offer conversion keeps catalog BasePrices (10/12).

#### H10 — Confirm-TOTAL guard: negotiated deal-level totals survive confirm (follow-up)
- **Problem:** The confirm-price guard preserved negotiated UNIT PRICES, but the handler still rebuilt `totalAmount = subtotal + tax + shipping` (`customer_orders_write.go:562` pre-this-round), so any accepted offer whose `TotalAmount != sum(unit×qty)` was still clobbered at confirm. This is frontend-reachable: `frontend/pages/admin/inquiries/[id].vue:247-256` exposes `unitPrice`/`quantity`/`totalAmount` as three independent required inputs, and `services/order/negotiation.go:148-158` stores them with NO invariant tying total to unit×qty. Concrete reproduction (arguer's): unit=2.5, qty=1000, total=2000 → intake (`orderintake/intake.go:205-208`) persists `Subtotal=2500`, `TotalAmount=2000`, `Source=inquiry`, and the trade is built from `order.TotalAmount` (`services/order/trade_from_order.go:25`) → 2000; confirm recomputed subtotal=2500 and persisted total=2500, so the negotiated total was lost AND the confirmed order disagreed with the intake trade (the H10 observable).

This makes the confirmed order's `TotalAmount` agree exactly with the intake-built trade. New helper `confirmLinesMatchDraft` (`customer_orders_write.go`) implements the "internally consistent" guard by product+quantity multiset: a negotiated total is authoritative only for the exact negotiated line set — an M-19 quantity override or added line invalidates it and the total falls back to a recompute from the preserved (and, for added lines, catalog) prices. KYB/credit checks now use the final `totalAmount`. For non-inquiry orders the recompute path is byte-for-byte unchanged (H1/H2 intact). `checkout_pricing.go`: extracted `resolveConfirmUnitPrice` (contract price list → base price → cost-stack → channel multiplier, `errRepriceNoPrice` guarded) shared by `repriceOrderItems` and the client-added-line branch of `priceInquiryConfirmItems` (previously priced from `BasePrice` only — a contract-price undercharge on B2B accounts). `priceInquiryConfirmItems` now also takes `userID`/`country` to resolve the contract list. `repository/order/order.go` confirmed unchanged — `confirmAndReserve` persists whatever financials the handler passes (`updates["total_amount"] = *fin.TotalAmount`, `order.go:599-600`).
- **Test:** `backend/internal/handlers/customer/customer_orders_write_negotiated_test.go` — three new full-`CustomerConfirmOrder` tests. `TestCustomerConfirmOrder_NegotiatedInquiryDiscountedTotalSurvives` (the arguer's required test): unit=2.5/qty=1000/total=2000 confirms with `TotalAmount=2000` (not 2500) and `Subtotal=2500` (line prices preserved) → FAILS on the pre-fix path with exactly the arguer's predicted 2500, PASSES post-fix. `TestCustomerConfirmOrder_NegotiatedInquiryQuantityOverrideRecomputes`: M-19 qty override to 2000 recomputes total to 5000 at the negotiated unit price (client price 999 discarded) — the negotiated 2000 is NOT frozen when the line set changes. `TestCustomerConfirmOrder_NegotiatedInquiryAddedLinePriced`: client-added p-2 is priced from the catalog cascade (BasePrice=12, client price 1 discarded) while negotiated p-1 keeps 2.5, total recomputed to 1450. The four prior negotiated tests and the normal-order control still pass.

#### H10 — Invoice-agreement guard: confirmed order stays internally consistent so the billing document honors the negotiated total (follow-up)
- **Problem:** The confirm-TOTAL guard made the confirmed order's `TotalAmount` equal the negotiated total (2000) but left `Subtotal` at the line-price sum (2500) with tax/shipping forced to 0 (`customer_orders_write.go:579-587`). This violates the `TotalAmount == Subtotal + Tax + Shipping` invariant the invoice-derivation path relies on. `AUTO_INVOICE_ON_PAYMENT` defaults TRUE (`config/config.go:225`), so on payment confirm `admin_payments.go:164-177` auto-derives an invoice via `CreateInvoiceFromOrder`; the manual endpoint `POST /invoices/from-order` (`admin_cross_border.go:329-340`) reaches the same derivation. `CreateInvoiceFromOrder` (`services/order/invoice_policy.go:90-102`) sets `Amount = ord.Subtotal` and `TotalAmount = ord.Subtotal + ord.TaxAmount + ord.ShippingAmount` → 2500 on a 2000 negotiated deal, so the customer-facing invoice over-bills by exactly the discount and disagrees with the order, the payment amount (`order.TotalAmount`, `gateway_payment.go:87,104`) and the intake trade. - **Fix:** `backend/internal/handlers/customer/checkout_pricing.go` — new pure helper `scaleInquiryLinesToTotal(items, total)` rescales the confirmed lines proportionally (unit × negotiated/line-sum, rounding residual absorbed into the last active line) so the quantity-weighted line sum equals the negotiated total, and returns the exact subtotal. `backend/internal/handlers/customer/customer_orders_write.go:579-591` — the total-preservation branch now calls `scaleInquiryLinesToTotal` and persists `Subtotal == TotalAmount == negotiated total` (tax/shipping stay 0, matching the intake draft/trade posture). This restores the invariant, so the derived invoice (`Amount = Subtotal`, `TotalAmount = Subtotal + Tax + Shipping`) bills the negotiated total, the invoice line items sum to the total, and order / invoice / payment / trade all agree. No-offer conversions and OEM drafts (`Subtotal == TotalAmount`) take the `scale == 1` no-op path and keep their negotiated unit prices byte-for-byte. Non-inquiry orders are untouched. `repository/order/order.go` confirmed unchanged (persists handler-supplied financials verbatim, `order.go:583-605`).
- **Test:** `backend/internal/handlers/customer/customer_orders_write_negotiated_test.go` — `TestCustomerConfirmOrder_NegotiatedInquiryDiscountedTotalSurvives` updated to assert the confirmed order is internally consistent (`Subtotal == 2000`, line `UnitPrice == 2.0` = 2000/1000, line sum == 2000, `TotalAmount == Subtotal + Tax + Shipping`); new `TestCustomerConfirmOrder_NegotiatedInquiryInvoiceBillsNegotiatedTotal` drives the REAL `CreateInvoiceFromOrder` over the confirmed order (via `fakeInvoiceRepo` implementing the 13-method `invoiceRepository`) and asserts `Amount == 2000` and `TotalAmount == 2000`. Both FAIL on the pre-fix path — the invoice test fails with `Amount = 2500`, exactly the arguer's billing reproduction — and PASS post-fix. All prior negotiated tests and the normal-order control still pass.
