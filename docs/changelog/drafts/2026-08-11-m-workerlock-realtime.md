# Changelog / Devlog — 2026-08-11 G28 Workerlock Lease Renewal + Bounded Realtime Startup
**Date:** 2026-08-11
**Source report:** [../../reports/code-review-audit-2026-08-11.md](../../reports/code-review-audit-2026-08-11.md)
**Scope:** backend Go / Gin / GORM
**Trigger:** G28: (a) `WithLock` acquires a lease with TTL equal to the work interval but never renews it, so a critical section longer than the TTL loses the lock and a second worker starts concurrently (mutual exclusion breaks); (b) `RedisBroadcaster` subscribe handshake runs on a background context, so it can block indefinitely when Redis drops the connection right after the startup Ping.
**Result:** Added lease renewal via a half-TTL heartbeat in `WithLock` (new `RedisLocker.Renew`, CAS Lua via PEXPIRE); bounded the realtime subscribe handshake with a 3s timeout. Regression tests added for both; targeted package build + tests pass.

## 2. Fixes in detail
#### G28(a) — Workerlock never renews (mutual exclusion breaks for long cycles)
- **Problem:** `backend/internal/pkg/workerlock/workerlock.go` `WithLock` acquired the lock with `ttl == work interval` and never extended it. A worker whose critical section ran longer than the TTL lost the lease mid-run, and a second instance's `Acquire` (SET NX EX) succeeded — two workers ran the same job concurrently, defeating the L-6 mutual exclusion that all five background workers in `cmd/api/main.go` rely on.
- **Fix:** Added `RedisLocker.Renew(ctx, key, token, ttl)` (`workerlock.go:105`) — an atomic Lua `GET == token → PEXPIRE`, returning `ErrLockNotHeld` when the lease is lost so the heartbeat can stop rather than extend someone else's lock. `WithLock` now starts a heartbeat goroutine (`renewLoop`, `workerlock.go:204`) that renews at half-TTL intervals while `fn` runs, and stops it (closing `stop` and draining `heartbeatDone`) in the deferred release path so a lease is never re-extended after `Release` deletes the key. Renewal is opt-in via a private `leaseRenewer` interface (`workerlock.go:128`) so the public `Locker` API is unchanged and `NoopLocker` (which never excludes anything) is untouched. Each renewal attempt is bounded by `min(ttl/2, 5s)` (`workerlock.go:221`, `renewAttemptTimeout` at `workerlock.go:35`) so a hung Redis cannot stall `WithLock` shutdown by more than 5s even for the 15-minute shipment-tracking TTL.
- **Tests:** `backend/internal/pkg/workerlock/workerlock_test.go` — `TestRedisLockerRenewExtendsTTL` (deterministic: miniredis `FastForward` past the original TTL, `Renew` keeps the lease), `TestRedisLockerRenewReportsLostLease` (expired/stale token → `ErrLockNotHeld`), `TestWithLockRenewsLeaseForLongCriticalSection` (end-to-end: fn held past TTL while miniredis clock is fast-forwarded; a competing `Acquire` must fail; lease released + heartbeat stopped after fn returns), `TestWithLockSkipsWhenHeld` (non-affected path). Verified the integration test fails on the pre-fix path (`competing Acquire succeeded … lease was not renewed`).
#### G28(b) — RedisBroadcaster startup can hang
- **Problem:** `backend/internal/pkg/realtime/redis.go:52-54` called `client.PSubscribe(relayCtx, …)` and `pubsub.Receive(relayCtx)` with `relayCtx = context.WithCancel(context.Background())` — no deadline. If Redis went away between the startup Ping and the subscribe, `Receive` blocked indefinitely (its read deadline comes from the ctx; a background ctx sets none), hanging the whole process at boot.
- **Fix:** The subscribe handshake now runs on its own `subCtx` with a 3s timeout (`redis.go:56-58`); `Receive(subCtx)` returns `context deadline exceeded` promptly and `NewRedisBroadcaster` fails with a wrapped error. A new shared `redisStartupTimeout` const (`redis.go:20`) also covers the Ping. The success path is unaffected — the relay's `Channel()` loop uses its own context, so cancelling `subCtx` after a successful handshake cannot disturb it.
- **Tests:** `backend/internal/pkg/realtime/redis_test.go` — `TestNewRedisBroadcasterSubscribeHandshakeIsBounded` (fake Redis answers PING + HELLO but accepts PSUBSCRIBE without ever sending the confirmation; startup must return within 8s — fails on the pre-fix path with `hung on the subscribe handshake`), `TestNewRedisBroadcasterHappyPathWithRedis` (miniredis: subscription confirmed, broadcaster usable), `TestNewRedisBroadcasterPingFailsBounded` (unreachable Redis fails within 6s).

**G28(a) audit (workerlock):**
- Root cause (lease never renewed → critical section longer than TTL loses the lease → second worker starts) is closed by the half-TTL heartbeat in `WithLock`. All 5 callers in `cmd/api/main.go` (trade-outbox-relay, order-draft-cleanup, abandoned-pending-order-cleanup, checkpoint-cleanup, shipment-tracking-sync) share this one fix point; no caller signature changed.
- Lease-loss path: `Renew` returns `ErrLockNotHeld` when the key expired or was taken over; `renewLoop` stops, and `WithLock`'s deferred `Release` swallows `ErrLockNotHeld` — the fixer's own instance can never DEL the second worker's lock (token CAS Lua). Correct.
- Drain-before-release: `close(stopHeartbeat)` + `<-heartbeatDone` guarantees `renewLoop` has fully exited before `Release` runs, so no PEXPIRE can land after the key is deleted. I traced the one subtle race (go select can pick `ticker.C` even after `stop` is closed → one extra bounded PEXPIRE) — this only extends the TTL that `Release` then deletes; no correctness impact.
- Shutdown bound: an in-flight `Renew` blocks the drain for at most `min(ttl/2, renewAttemptTimeout)` = ≤5s even for the 15-min shipment-tracking TTL. Verified.
- No data races: all cross-goroutine state is channel-based (stop/`heartbeatDone`); token is immutable. `-race` unavailable (CGO_ENABLED=0) but the design has no shared mutable state.
- Side benefit not claimed by the fixer: because the lock is now held for the whole critical section, a single instance can no longer overlap its own ticks when `fn` runs longer than the tick interval (pre-fix the same instance's next tick would re-Acquire the expired lock and run a second concurrent `fn`).
- Non-blocking edge cases (inherent, not fix gaps): (1) if Redis partitions for longer than the TTL, every `Renew` fails and the lease expires regardless — lease-based mutual exclusion cannot prevent this without fencing tokens; the heartbeat correctly stops on `ErrLockNotHeld`. (2) On graceful shutdown the deferred `Release` runs with a parent ctx that is already cancelled, so the lock may persist until its (possibly just-renewed) TTL expires and could delay the next instance's initial tick after a restart — pre-existing TTL-based self-healing behavior, same order of magnitude as before the fix, not a regression.

**G28(b) audit (realtime):**
- The subscribe handshake (`PSubscribe` + `Receive`) now runs on a 3s `subCtx`; `Receive(subCtx)` returns a context-deadline error instead of blocking. Failure path cleans up `relayCancel()`, `pubsub.Close()`, `client.Close()`. Worst-case boot is bounded to ~6s (3s ping + 3s subscribe) — fail-fast per the finding.
- I verified against the vendored go-redis v9.19 source that cancelling `subCtx` after a successful handshake CANNOT disturb the relay: `channel.initMsgChan` and `initHealthCheck` use `context.TODO()`; the `Channel()` loop's `Receive(context.TODO())` derives its read deadline from the TODO ctx (no deadline), not from the stale `c.cmd` created with `subCtx` (`Conn.WithReader` computes the deadline from the ctx argument, and `cmd.ctx` is only used for logging). The happy-path test confirms the relay delivers messages after `subCancel()` has fired.
- Non-blocking note: `handlers.New` returns an error on broadcaster failure and `main.go` calls `log.Fatalf`, so with the fix a down Redis at boot now exits with a clear error instead of hanging — consistent with the documented operational gotcha (backend hard-fails when `REDIS_URL` is set and Redis is down). Acceptable resolution of the "hang" finding; a degrade-to-Hub fallback would be gentler but was not required.

**Tests:** Regression tests genuinely exercise the fix — `TestWithLockRenewsLeaseForLongCriticalSection` fails on the pre-fix path (the competing Acquire succeeds when the lease is never renewed) and `TestNewRedisBroadcasterSubscribeHandshakeIsBounded` hung 8s pre-fix. The fixer's note that the fake-Redis test requires a proper HELLO flat-array reply for go-redis v9.19 is correct (otherwise initConn fails before the silent PSUBSCRIBE and the test passes for the wrong reason).
