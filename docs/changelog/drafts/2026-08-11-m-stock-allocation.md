## 2. Fixes in detail

#### G21-a — Transfer to warehouse with no warehouse_stock row silently dropped stock (round 2: TOCTOU + reserved)
- **Problem:** `order_stock_allocate.go` `TransferStockBetweenWarehouses` added the transferred quantity with a plain `UPDATE ... WHERE warehouse_id=? AND product_id=?`. When the target warehouse had no `warehouse_stock` row the UPDATE matched 0 rows and the transferred stock vanished with no error. The round-1 helper (`addStockToWarehouseUpsert`) fixed the silent drop with a First-then-Create/Update, but that was a TOCTOU (two concurrent transfers into an empty target both read ErrRecordNotFound; the loser's Create hit the `idx_wh_prod` unique index and errored) and it created the target with `Reserved=0`, dropping the customer reservations that sat on the moved goods (target sellable inflated).
- **Fix (round 2):** `TransferStockBetweenWarehouses` first reads the source row with `clause.Locking{Strength:"UPDATE"}` (serializes concurrent transfers of the same product) and computes `moveReserved = min(qty, source.Reserved)`; `deductWarehouseStock` drains the source reserved (reserved-first semantics); the target is then upserted by `addStockToWarehouseUpsert(tx, to, product, qty, moveReserved, t)` which is a single atomic `INSERT ... ON CONFLICT (warehouse_id, product_id) DO UPDATE SET quantity = warehouse_stocks.quantity + excluded.quantity, reserved = warehouse_stocks.reserved + excluded.reserved, updated_at = excluded.updated_at` — no read-then-create race, reserved travels with the goods, and the expression is portable between PostgreSQL and the SQLite test driver. The test schema now declares `UNIQUE(warehouse_id, product_id)` (mirrors `idx_wh_prod`) so the SQLite driver exercises the same ON CONFLICT path.

#### G21-b — FEFO warehouse-sync failures were log-only
- **Problem:** both FEFO paths (`deductFEFOFromBatches` and `deductFEFOFromBatchesWithWarehouse`) synced the `warehouse_stock` mirror with `log.Printf` on failure and no `RowsAffected` check, so a missing/insufficient mirror row reported success while the warehouse stock never moved.
- **Fix:** added `syncFEFOWarehouseStock` which returns an error on DB failure and on `RowsAffected==0` (row missing or insufficient). Both FEFO paths now return that error so the caller's transaction rolls back the batch deduction instead of committing a partial result. Removed the now-unused `log` import.

#### G21-c — deductWarehouseStock never decremented Product.StockQuantity
- **Problem:** `deductWarehouseStock` read `Product.StockQuantity` but never decremented it (audit `StockAfter` also echoed `beforeP`), so a direct deduction drifted product-level stock away from warehouse-level stock.
- **Fix:** added a `reserved bool` parameter. When `false` (direct deduction, no prior reservation) `Product.StockQuantity` is decremented atomically with a `stock_quantity >= qty` conditional update and `StockAfter` reflects it; when `true` (goods already reserved, so `reserveWarehouseStock` already decremented product stock) the aggregate is left untouched. Callers: `applyWarehouseStockChange` deduct reasons pass `false`; `FulfillmentRepository.Create` passes `order.StockReserved`; `TransferStockBetweenWarehouses` passes `true` (transfer is net-zero at product level). Replaced the PostgreSQL-only `GREATEST()` clamp with portable `CASE WHEN` so the sqlite test driver exercises the same SQL.

#### G21-d — Double deduction between fulfillment and logistics dispatch (round 2: close the concurrency window)
- **Problem:** the same order's stock could be deducted twice — once by `FulfillmentRepository.Create` (goods_issued) and once by `LogisticsService.DispatchShipment` (dispatched). Dispatch also discarded the stock-audit records it produced. Round 1 fixed the sequential case (deduct only `item.Quantity - item.FulfilledQuantity`, write `StockReasonDispatched` audit rows, fulfillment skips when present), but the refutation was correct that round 1 still read the order OUTSIDE the transaction (`logistics.go` `FindByID`) and iterated that stale snapshot inside the tx with no order-row lock and no re-read — so a fulfillment committing between the snapshot read and the deduction still caused a full re-deduction.
- **Fix (round 2, `logistics.go`):** the outer `FindByID` is kept only as a cheap existence check; inside the transaction, after the PENDING→DISPATCHED claim, the order row is re-read with `tx.Clauses(clause.Locking{Strength:"UPDATE"})` and the deduction math uses that fresh copy. `FulfillmentRepository.Create` already takes the same FOR UPDATE order lock, so the two flows now contend on a shared lock and serialize: if the fulfillment wins the lock first its `FulfilledQuantity` is visible in the dispatch's re-read (only the remainder is deducted) and if the dispatch wins first the fulfillment later sees the `StockReasonDispatched` audit rows and skips its deduction. The two paths deduct exactly once in every interleaving. No lock cycle is possible: dispatch holds the shipment-row lock then the order-row lock, fulfillment holds only the order-row lock.
- **Fix (round 3, `logistics.go` — dispatch↔dispatch on the same order):** the round-2 order-row lock serializes dispatch against fulfillment but NOT one dispatch against a second dispatch of a different shipment on the same order. Because `ShipmentTracking` has no quantity field, the first dispatch issues the whole unfulfilled remainder and a second dispatch recomputes `item.Quantity - item.FulfilledQuantity` against the same (never-bumped) `FulfilledQuantity`, re-deducting the order's stock. In `DispatchShipment`, after the FOR UPDATE order re-read, the transaction now counts existing `stock_transactions` rows with `reference_id = order.ID AND reason = 'dispatched'` (`priorDispatch`); when `priorDispatch > 0` the physical deduction loop is skipped entirely (the goods already left the warehouse at the first dispatch) while the PENDING→DISPATCHED claim, the dispatch event, and the order-status advance still proceed. The order-row FOR UPDATE lock serializes two concurrent dispatches on the same order, so the count sees the first dispatch's committed audit rows before the second proceeds — the guard is race-free and the deduction is idempotent per order. `FulfillmentRepository.Create` already used the same `reference_id + reason='dispatched'` probe, so the dispatch and fulfillment paths now share one idempotency primitive.

#### G21-e — FulfillmentRepository.Ship had no row lock
- **Problem:** `Ship` read the order row without `FOR UPDATE`, and two concurrent ships of different fulfillments of the same order could both increment `ShippedQuantity` from the same stale snapshot, losing an update.
- **Fix:** the fulfillment status transition is now a conditional `UPDATE ... WHERE status IN ('packed','pending')` with a `RowsAffected==0` → error guard (only one caller wins the transition), and the order row is read with `Clauses(clause.Locking{Strength:"UPDATE"})` so concurrent ships serialize before reading `order.Items`. Concurrent ships of the same fulfillment now fail cleanly instead of double-incrementing.

#### G21-f — Draft-cleanup worker can lose audit rows (NOT edited — outside owned files)
- **Problem:** `ReleaseExpiredPendingConfirmationOrders` (in `internal/repository/order/order.go`) swallows the `writeStockAuditEntries` error with `log.Printf`, so on write failure the stock release and order cancellation still commit while the release's audit rows are lost.
- **Fix (recommended, for the owner of `order.go`):** change
  ```go
  if ae := writeStockAuditEntries(tx, allAudit); ae != nil {
      log.Printf("order: writeStockAuditEntries failed: %v", ae)
  }
  ```
  to return the error from the per-order transaction:
  ```go
  if ae := writeStockAuditEntries(tx, allAudit); ae != nil {
      return ae
  }
  ```
  The existing per-order transaction wrapper already logs-and-continues on error (line ~674), so propagating the audit failure rolls back that order's stock release/cancel while still processing the remaining batch. `order.go` is not among this task's owned files, so this change was not applied here.
