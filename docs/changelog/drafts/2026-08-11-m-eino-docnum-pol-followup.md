## 2. Fixes in detail

#### G29(c) — Collision-resistant document-number generation
- **Problem:** `backend/internal/pkg/eino/graph/pipeline.go` — `NewBatchDocSeq` derived `seq := int(now.UnixMilli() % 100000)` (residue 0 coerced to 1). Two generation batches in the same millisecond (concurrent SSE connections / parallel agent runs), or any two batches exactly 100,000 ms apart on the same day (each residue recurs ~864×/day → birthday collisions near-certain at a few hundred batches/day), shared the same `Date`+`Seq`. `TradeDocument.DocNumber` has a GLOBAL `uniqueIndex` (`models/trade/trade.go:69`, not scoped to `TransactionID`), so the colliding `AddDocument` (`PersistDocs`) hit a UNIQUE violation, the error was appended only to `state.Errors`, and the doc was silently dropped (status `partial`). The old `TestNewBatchDocSeq` asserted only the modulo semantics and could not catch the collision.
- **Fix:** `pipeline.go` — introduced `docSeqCounter atomic.Uint64`, seeded in `init()` with `time.Now().UnixMilli() % 100000`, and `NewBatchDocSeq` now returns `int(docSeqCounter.Add(1))` (guarded `>= 1`). Seq is strictly increasing per batch within the process and never reduced modulo anything, so `Date`+`Seq` is unique for every batch and the global unique index cannot be tripped by same-day batch collisions. Regression tests in `graph/pipeline_test.go`: `TestNewBatchDocSeq_Uniqueness` (same-ms and 100 s-apart-same-day both FAIL pre-fix, PASS post-fix) and `TestDocumentBatch_CollisionResistantDocNumbersPersist` (two colliding batch identities driven through a real sqlite-backed persister with the unique index migrated; FAILS pre-fix on the identical DocNumber / UNIQUE constraint, PASSES post-fix with 2 rows).

#### G29(d) — CI `pol` field filled with an Incoterms term; BL hardcodes a port
- **Problem:** `pipeline.go` — the CI template rendered `"pol": %q` from `input.Incoterms` (default `"FOB Shanghai"`), i.e. the port-of-loading field held a term, not a port; `"pod"` was the literal `"Destination Port"`. The persisted CI JSON is read by LC validation and customs-styled docs, so a legal/financial document carried an Incoterms string as a port. The `BILL_OF_LADING` template hardcoded `"port_of_loading": "Shanghai"` while the SLI hardcoded `"origin_port": "Shanghai"` and the insurance `route` hardcoded `"Shanghai to Destination Port"` — so CI and BL disagreed structurally, and `DocGenerationInput` had no port field at all for a real port to flow through.
- **Fix:** `pipeline.go` — added `PortOfLoading` / `PortOfDestination` to `DocGenerationInput`; `PrepareContext` defaults them to `"Shanghai"` / `"Destination Port"`. The CI now renders `pol` ← `PortOfLoading`, `pod` ← `PortOfDestination`, and keeps the term on a new `"incoterms"` key; the BL `port_of_loading`/`port_of_discharge`, the SLI `origin_port`/`destination_port`, and the insurance `route` ("%s to %s") all read the same port fields, so every customs-styled doc agrees. Regression tests in `graph/pipeline_test.go`: `TestDocumentBatch_CIPolAndBLPortsComeFromInput` (explicit Qingdao/Hamburg ports, asserts CI pol/pod + BL ports, FAILS pre-fix: `CI pol = "CIF Rotterdam"`) and `TestDocumentBatch_PortsDefaultWhenAbsent` (absent ports default and `pol` never equals the incoterms term, FAILS pre-fix: `default CI pol = "FOB Shenzhen"`).

#### G29 latent — LLM tool schema does not yet advertise the port params
- **Problem:** the `generate_trade_documents` tool schema (`graph/tool.go` `Info()`) still lists only `incoterms` and friends; an LLM caller cannot learn that `port_of_loading` / `port_of_destination` are accepted, so it will usually omit them and the defaults (`"Shanghai"`/`"Destination Port"`) apply.
- **Response:** `graph/tool.go` is outside the owned-file set for this round, so the schema was not touched. This is not a regression of (d): the structural defect (port field holding a term, CI/BL disagreement) is closed — with no ports supplied the CI/BL now render the default ports, never the Incoterms term. Extending `tool.go` `ParamsOneOf` is a small follow-up for the graph/tool owner.

Within a single process the pair `(Date, Seq)` is provably unique for every batch: Seq never repeats, and Date comes from the live `time.Now()` passed at `pipeline.go:114`. Both agents — TradeAssistant (`agent.go:42`) and B2B coordinator (`deep_b2b.go:44`) — call `graph.NewDocumentPipelineGraph` from the same process and share the same package-level counter, so concurrent batches across either agent cannot share Date+Seq. **G29(d) — closed.** `pipeline.go:92-97` (`PrepareContext`) defaults `PortOfLoading`/`PortOfDestination`; `pipeline.go:277-280` renders CI `pol`/`pod` from those ports with the term kept on a separate `"incoterms"` key; `pipeline.go:337-340`, `:353-357`, `:365` render BL `port_of_loading`/`port_of_discharge`, SLI `origin_port`/`destination_port`, and insurance `route` from the same fields. `pol` can never carry an Incoterms term again, and CI/BL agree by construction. 3. **Global `uniqueIndex` retained** (`models/trade/trade.go:69`) — intentional; doc numbers are globally-referenced identity strings, and the generator is the correct fix point. No same-process scenario trips it anymore.
