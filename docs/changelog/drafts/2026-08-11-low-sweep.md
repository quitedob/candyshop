## 2. Fixes in detail
#### G-LOW-1 — verify-email.vue: token type guard
- **Problem:** `frontend/pages/auth/verify-email.vue:87` force-cast `route.query.token as string`. Vue Router types the query value as `string | string[] | null`, so a duplicated `?token=a&token=b` would hand an array to `verifyEmail(token: string)` at runtime.
- **Fix:** Take the first value when the param is an array (`Array.isArray(rawToken) ? rawToken[0] : rawToken`) and guard on truthiness before calling `verifyEmail`.
#### G-LOW-2 — forgot-password.vue: only set success on a real response
- **Problem:** `frontend/pages/auth/forgot-password.vue:88-91` set `success = true` in the `catch`, so a network/5xx failure showed the "email sent" alert. The backend intentionally returns 200 for both known and unknown emails (anti-enumeration), so the only throws are genuine failures and must not be reported as success.
- **Fix:** Added an `error` ref, rendered with the existing `auth-alert--error` + `role="alert"` pattern (same as `login.vue`/`reset-password.vue`); the catch now surfaces `err.data.message || t('errors.api.request_failed')` and never clears the email / claims success.
#### G-LOW-3 — contact.vue: off-by-one FAQ index guard
- **Problem:** `frontend/pages/contact.vue:309` guarded `items.length >= 4` while the code accesses `items[4]` (needs >= 5); a 4-item FAQ list would crash on `rt(undefined.question)`.
- **Fix:** Guard raised to `items.length >= 5` (covers both `items[4]` and `items[2]`).
#### G-LOW-4 — faq.vue: page blank unless exactly 15 items
- **Problem:** `frontend/pages/faq.vue:96` required `items.length === 15`; any count change rendered the page blank.
- **Fix:** Render whatever exists: `slice(0, cats.length)` with `cats[index] || 'general'` fallback so fewer/more items never blank the page; the canonical 15-item category mapping is preserved.
#### G-LOW-5 — blog/index.vue: list clamp silent truncation (blog half; cases half = follow-up, see §5)
- **Problem:** `frontend/pages/blog/index.vue:182` requested `limit: 200` but the backend clamps page size to 50 (`pagination.ParsePagination(c, 10, 50)`), silently truncating the category list / featured post input. The original finding also named the **cases** list page, which is a separate file (`cases-clients/index.vue`) outside this agent's owned set.
- **Fix (blog):** Request the real page size (50) and page through `pagination.totalPages` to surface the actual total for the category filter list; single request when the set fits in one page.
- **Status:** Blog half verified against the backend (`totalPages` populated at `backend/internal/services/content/content.go:57` and `:117`). Cases half not touchable here — see §5.
#### G-LOW-6 — ProductCard.vue: nested buttons + hover-hidden focusable controls
- **Problem:** `frontend/components/product/ProductCard.vue` nested three `<button>`s inside a `<NuxtLink>` (invalid interactive nesting); quick-action buttons were `opacity: 0` until hover yet remained keyboard-focusable and clickable while invisible.
- **Fix:** Moved the quick-action buttons and the inquiry button out of the link as siblings; the card is now `position: relative` and the actions sit over the image. Quick actions get `pointer-events: none` when hidden and reveal on hover **or** `:focus-within`/card focus (matching the repo's Header `:focus-within` pattern), so keyboard users never hit invisible controls; touch (`@media (hover: none)`) still always shows them.
