## 2. Fixes in detail
#### G24a — Soft-delete-aware unique indexes on users.email / products.slug
- **Problem:** `internal/models/user/user.go:28` and `internal/models/product/product.go:32` declared full-table unique indexes, so a soft-deleted row's email/slug can never be reused — re-registration/re-creation hit a 5xx unique-constraint error.
- **Fix:** Switched both to GORM partial unique indexes scoped to live rows: `uniqueIndex:idx_users_email_active,where:deleted_at IS NULL` (user.go) and `uniqueIndex:idx_products_slug_active,where:deleted_at IS NULL` (product.go). New index names avoid clashing with a pre-existing index on already-migrated DBs. Regression tests `internal/models/user/user_test.go` (`TestSoftDeletedEmailCanBeReused`) and `internal/models/product/product_test.go` (`TestSoftDeletedSlugCanBeReused`) soft-delete then recreate the same email/slug and assert the second insert succeeds and the live lookup returns the new row.
- **Deployed-DB DDL hook (second pass):** GORM AutoMigrate does not drop removed indexes, so the pre-G24a full-table `idx_users_email` / `idx_products_slug` survive on every already-migrated database and still block reuse. Since GORM v1.30.0 exposes no model `AfterMigrate` hook (verified in the module source), the DDL hook is now shipped as tested, idempotent helpers in the owned model packages: `user.DropLegacyEmailUniqueIndex` / `product.DropLegacySlugUniqueIndex` (HasIndex-guarded, no-op when absent, safe to call on every startup and on fresh DBs), with the legacy index names exposed as `user.LegacyUniqueIndexEmail` / `product.LegacyUniqueIndexSlug`. Regression tests `TestDropLegacyEmailUniqueIndex_UnblocksReuse` and `TestDropLegacySlugUniqueIndex_UnblocksReuse` simulate the deployed state (legacy index present), prove reuse is blocked (the production 5xx symptom), then drop the legacy index and prove reuse succeeds.
#### G24a — startup migration wiring in database.go (follow-up round, closes the deployed-DB blocker)
- **Problem:** `database.AutoMigrate` (the startup migration `cmd/api/main.go:73` calls) never invoked the shipped `DropLegacyEmailUniqueIndex` / `DropLegacySlugUniqueIndex` helpers — they were dead code (grep showed only their definitions + tests referenced them). GORM v1.30.0 AutoMigrate never drops indexes removed from a model, so on every already-migrated Postgres DB the pre-G24a full-table `idx_users_email` / `idx_products_slug` still enforced uniqueness across soft-deleted rows and re-registering a deleted email / re-creating a deleted slug still raised the 5xx unique-constraint error.
- **Fix:** `database.go` `AutoMigrate` now calls `dropLegacyUniqueIndexes(db)` after Phase 2 (and the pgvector-gated ProductEmbedding migrate), just before the "Database migration completed" log; the helper wires the two idempotent, HasIndex-guarded model helpers (`user.DropLegacyEmailUniqueIndex`, `product.DropLegacySlugUniqueIndex`) and wraps their errors with context. It is a no-op on fresh databases and on deployments that already dropped the legacy indexes, so it is safe on every startup.
- **Tests (new):** `internal/database/database_migrate_index_test.go` — `TestAutoMigrate_DropsLegacyUniqueIndexes_UnblocksReuse` simulates an already-migrated DB (legacy full-table indexes present), proves reuse is blocked (the exact 5xx symptom), then drives the PRODUCTION `AutoMigrate` and asserts both legacy indexes are gone and email/slug reuse succeeds — this test FAILED on the pre-fix tree (`AutoMigrate did not drop legacy products.slug unique index (G24a wiring missing)`) and now passes. `TestAutoMigrate_FreshDatabaseDropIsNoop_ReuseWorks` guards the fresh-DB no-op so the wiring cannot regress new deployments.
#### G24b — Write product_embeddings (embedding upsert + self-healing backfill)
- **Problem:** `internal/repository/product/product.go` never wrote to `product_embeddings`, so `SearchVectorSimilar`'s JOIN was always empty and semantic search silently fell back to keyword.
- **Fix:** Added `ProductRepository.UpsertEmbedding(ctx, productID, embedding)` (ON CONFLICT product_id DO UPDATE, no-op on empty input) and `FindProductsMissingEmbeddings(ctx, limit)` (active, non-deleted products without an embedding row). Added `SearchService.ensureProductEmbeddings` in `internal/services/search/search.go`, called from `semanticProductSearch`, that lazily backfills missing embeddings (name + summary text, bounded batch, `sync.Mutex.TryLock` to prevent API stampedes, failures logged never propagated so keyword stays the fallback). New products are picked up by the next semantic search. Tests `TestUpsertEmbedding_InsertsThenUpdates` and `TestFindProductsMissingEmbeddings` in `internal/repository/product/product_test.go`.
- **Dimension guard (second pass, addresses "silently reproducing inert semantic search"):** the embedding column is fixed at `vector(1536)`, so a configured model whose output dim ≠ 1536 can never be stored on Postgres yet is silently accepted by SQLite. `modelsProduct.EmbeddingDim` is now the single source of truth (declared next to the column tag). `UpsertEmbedding` rejects a mismatched length with a descriptive error naming the product, the actual dim, and the required 1536 — consistent across dialects instead of Postgres-only. `SearchService` now checks the generated embedding dim on both the query path and the backfill path and logs a once-per-process `Warning: embedding model %q returned %d dimensions, want 1536 (vector(1536)); semantic search disabled...` so the inert symptom is diagnosable rather than silent. New tests `TestUpsertEmbedding_RejectsWrongDimension` (error surfaced, no row written; fails on the pre-fix path where SQLite silently accepted any dim) plus updated 1536-dim vectors in the two existing embedding tests.
#### G24c — Tax/shipping fail closed on rate-lookup DB errors (service layer, the finding's cited lines)
- **Problem:** `internal/services/order/tax.go` and `internal/services/order/shipping.go` treated any `FindBestRate` error — including a real DB failure — as "no rate configured", returning 0 tax/shipping with a nil error (under-collection).
- **Fix:** In `CalculateTaxWithFlag` and `CalculateShippingCostWithFlag`, `gorm.ErrRecordNotFound` still yields the not-configured flag with a nil error (M-10/M-11 behavior preserved), but any other error is wrapped and returned so checkout can surface the lookup failure. New tests in `internal/services/order/tax_test.go` and `shipping_test.go` cover the DB-error (fail closed), no-rate (still flag-only), and happy-path cases via stub repositories. Added wrapper-level tests (`TestCalculateTax_WrapperPropagatesDBError`, `TestCalculateShippingCost_WrapperPropagatesDBError`, `TestCalculateShippingCostWithIncoterms_PropagatesDBError`) pinning that the 4-arg convenience APIs the confirm handler calls surface the error and never re-collapse it.
- **Scope note (end-to-end):** the confirm-time money caller `computeCheckoutPricing` (`backend/internal/handlers/customer/checkout_pricing.go`) still discards the propagated error and `cart.go` books the order with 0 tax / 0 shipping. Those files are OUTSIDE this fixer's owned-file list; the exact change spec is in §5 point 1. The estimate/shipping handlers (`cart_estimate.go`, `customer_shipping.go`) now fail closed (pending_rates / 500) — verified, no regressions.
